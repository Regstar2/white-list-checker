# WhiteListChecker — scope версии 1.0

## Проблема

WhiteListChecker помогает проверить, как мобильная сеть фактически достигает контрольных ресурсов, и обнаружить наблюдаемые признаки режима белых списков. Приложение не имеет доступа к внутренним правилам оператора и не утверждает, что такой режим включён наверняка.

## Главный пользовательский сценарий

1. Пользователь оставляет Wi‑Fi включённым или отключает его.
2. Приложение явно получает cellular `Network` через `ConnectivityManager.requestNetwork(...)`.
3. DNS и HTTPS-проверки выполняются через полученный cellular-маршрут.
4. Сайты дают основной классификационный сигнал; DNS используется как дополнительная диагностика.
5. Результат сохраняется локально и доступен в истории, статистике и диагностике.

## Что входит в 1.0

- ручная проверка мобильной сети;
- редактируемые списки `LOCAL` / `FOREIGN` сайтов;
- редактируемые списки DNS resolver;
- raw DNS по UDP/53 с TCP/53 fallback;
- hostname fallback через `Network.getAllByName(...)` на cellular `Network`;
- HTTPS target checks через network-bound socket factory с обычной TLS/hostname verification;
- локальная история, статистика и timeline в Room;
- локальные Android-уведомления;
- WorkManager background checks;
- foreground active monitoring;
- личные Telegram-уведомления и команды через user-owned Cloudflare Worker;
- интерфейс RU/EN.

## Что не входит

- центральный/public service владельца проекта;
- общий Telegram-бот проекта;
- отправка агрегированных отчётов на сервер проекта;
- device linking к центральному сервису;
- центральные remote commands;
- proxy/VPN transport для основного checker path.

## Сетевая граница

`Proxy support: N/A by project-specific design — WhiteListChecker измеряет прямой маршрут cellular-сети; прокси/VPN изменяет измеряемый транспорт и может сделать результат диагностики недостоверным.`

Поэтому proxy/VPN не добавляется в основной путь проверки. Это проектное исключение из общего `NETWORK_PROXY_STANDARD.md`, а не отсутствующая функция checker.

Отдельные необязательные интеграции, не являющиеся измерением cellular-маршрута, должны документировать собственную transport policy. Текущий личный Telegram relay использует обычный HTTPS к Worker пользователя.

## Хранение данных и обновление

Room schema v8 хранит локальную историю, статистику, timeline и очередь личных Telegram-сообщений. Миграция `7 -> 8` при обновлении с `0.10.4` удаляет только устаревшую таблицу `pending_public_reports`.

Физическая проверка обновления `0.10.4 -> 1.0.0` без очистки данных подтвердила сохранение истории и удаление UI общего сервиса.

## Ограничения

- классификация является эвристикой по наблюдаемому поведению сети;
- VPN/tunnel меняет маршрут и делает результат checker нерепрезентативным для прямого cellular-доступа;
- raw DNS/53 не шифруется;
- блокировка UDP/53 и TCP/53 может сделать отдельный configured resolver недоступным;
- WorkManager не гарантирует точное время выполнения;
- Android может ограничивать foreground service;
- личный Telegram требует собственного Worker и Telegram-бота пользователя.
