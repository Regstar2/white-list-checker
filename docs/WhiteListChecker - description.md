# MVP: Android-приложение для определения включения/выключения БС

## Цель MVP

Приложение должно:

```
1. Проверять именно мобильную сеть, даже если активен Wi-Fi.2. Определять состояние:   - БС выключены   - БС включены   - мобильного интернета нет   - странная частичная проблема3. Отслеживать только переходы:   - БС выключены → БС включены   - БС включены → БС выключены4. Отправлять уведомление в Telegram через локальный HTTP/SOCKS-прокси.5. Не отправлять Telegram напрямую вообще.6. Сохранять неотправленные уведомления в очередь.
```

# v0.1 — ручная проверка мобильной сети

## Задача

Сделать кнопку:

```
[Проверить мобильную сеть]
```

И вывести результат на экран.

## Что реализовать

### 1. Запрос мобильной сети

Класс:

```
CellularNetworkProvider
```

Ответственность:

```
- запросить TRANSPORT_CELLULAR через ConnectivityManager- вернуть Network- если мобильная сеть недоступна, вернуть ошибку
```

### 2. Проверка сайтов через конкретный Network

Класс:

```
MobileSiteChecker
```

Проверяет:

```
Google / внешний сайтYandex / локальный сайт
```

Через:

```
network.openConnection(...)
```

Не через обычный OkHttp без привязки, иначе Android радостно отправит всё через Wi-Fi. Потому что зачем делать очевидное очевидным.

### 3. Простой классификатор

Класс:

```
WhitelistStateClassifier
```

Логика MVP:

```
Google доступен + Yandex доступен → БС выключеныGoogle недоступен + Yandex доступен → БС включеныGoogle недоступен + Yandex недоступен → мобильного интернета нетGoogle доступен + Yandex недоступен → частичная проблема
```

# v0.3 — отслеживание включения/выключения БС

## Задача

Не просто показывать статус, а понимать изменение состояния.

Отправлять нужно только:

```
БС выключены → БС включеныБС включены → БС выключены
```

## Добавить хранение состояния

Класс:

```
MonitorStateRepository
```

Хранить в DataStore:

```
lastConfirmedStatependingStatependingStateCountlastNotificationAtlastCheckAt
```

## Антидребезг

Правило:

```
новый статус должен подтвердиться 2 раза подряд
```

Пример:

```
1 проверка: БС включены2 проверка: БС включены→ считаем статус подтверждённым→ отправляем уведомление
```

Если:

```
1 проверка: БС включены2 проверка: частичная проблема3 проверка: БС выключены
```

ничего не отправляем.

## Класс

```
StateChangeDetector
```

Он принимает текущий статус и сохранённое состояние.

Возвращает:

```
NoChangeConfirmedChange(oldState, newState)
```

## Результат v0.3

Приложение уже умеет отслеживать именно события включения/выключения БС, а не спамить каждую проверку.

# v0.4 — Telegram через локальный прокси

## Задача

Связать приложение с Telegram Bot API, но **только через локальный прокси**.

Прямой доступ к Telegram запрещён.

## Настройки

Экран:

```
TelegramBot token: ********Chat ID: ********Proxy type:- HTTP- SOCKSProxy host:127.0.0.1Proxy port:1080[Проверить связь с Telegram]
```

## Классы

```
TelegramSettingsRepositoryTelegramProxySettingsTelegramHttpClientFactoryTelegramNotifierTelegramReportFormatter
```

## Логика

```
1. Пользователь вводит bot token.2. Пользователь вводит chat id.3. Пользователь вводит локальный proxy.4. Приложение вызывает getMe через proxy.5. Если успешно — Telegram настроен.6. При смене БС приложение вызывает sendMessage через proxy.
```

## Важное правило

```
TelegramNotifier не должен иметь режима direct.
```

То есть не так:

```
proxy не работает → попробуем напрямую
```

А так:

```
proxy не работает → сохранить отчёт в очередь
```

## Результат v0.4

При включении/выключении БС приложение отправляет уведомление в Telegram через локальный прокси.

# v0.5 — очередь неотправленных уведомлений

## Задача

Если прокси не работает, Telegram не доступен или токен временно не проходит, событие нельзя терять.

## Добавить очередь

Класс:

```
PendingTelegramReportRepository
```

Можно начать с DataStore/JSON. Room пока не обязателен, нечего тащить базу данных ради трёх сообщений, мы не банк пишем.

Модель:

```
data class PendingTelegramReport(	val id: String,	val text: String,	val createdAt: Long,	val attemptCount: Int,	val lastError: String?)
```

## Логика

```
если sendMessage успешен:    ничего не сохраняемесли sendMessage упал:    сохраняем отчёт в очередьпри следующем запуске проверки:    сначала пробуем отправить старые отчёты    потом отправляем новый отчёт
```

## Ограничения

```
максимум 20 отчётов в очередистарше 7 дней удалятьпосле 10 неудачных попыток помечать как failed
```

## Результат v0.5

Приложение не теряет событие смены БС, даже если локальный прокси временно не работает.

# Главный технический риск

Самое слабое место:

```
локальный proxy на Android
```

Не каждый клиент даёт другим приложениям доступ к локальному порту. Поэтому в MVP обязательно нужна кнопка:

```
[Проверить прокси]
```

И честный статус:

```
SOCKS 127.0.0.1:1080 доступенTelegram API доступенТокен валиден
```

или:

```
Прокси недоступен.Telegram-уведомления будут сохраняться в очередь.Прямое подключение отключено.
```
