# Cursor prompt: Whitelist Checker Android MVP v0.6

Доработай Android-приложение Whitelist Checker с версии v0.5 до v0.6.

Главная цель v0.6: добавить автоматическую периодическую проверку состояния белых списков через WorkManager.

После v0.5 приложение уже умеет:

```text
1. Ручную проверку мобильной сети.
2. Проверку FOREIGN/LOCAL групп сайтов через cellular Network.
3. Классификацию состояния БС.
4. Антидребезг: 2 одинаковых новых состояния подряд.
5. Отправку Telegram-уведомлений через локальный HTTP/SOCKS-proxy.
6. Запрет direct Telegram fallback.
7. Очередь неотправленных Telegram-сообщений в Room.
8. Ручную повторную отправку очереди.
```

В v0.6 нужно добавить фоновую периодическую проверку, чтобы приложение могло само отслеживать включение/выключение БС без ручного нажатия кнопки.

Не добавляй foreground service, VPN service, Telegram-команды, FCM, свой сервер и прочую инфраструктурную помойку. Нам нужен WorkManager, а не маленькая копия дата-центра в телефоне.

## 2. Важное ограничение WorkManager

Периодическая работа через WorkManager не предназначена для секундных или минутных проверок.

Минимальный нормальный интервал:

```text
15 минут
```

Не пытайся сделать 1 минуту через WorkManager. Android всё равно будет смеяться, душить процесс и делать вид, что так и было задумано.

В v0.6 разрешённые интервалы:

```text
15 минут
30 минут
60 минут
```

## 7. WhitelistCheckWorker

Создай Worker:

```kotlin
class WhitelistCheckWorker : CoroutineWorker
```

Ответственность:

```text
1. Отметить старт фоновой проверки.
2. Выполнить CheckAndNotifyUseCase.
3. Сохранить результат последней фоновой проверки.
4. Вернуть Result.success(), если логика отработала.
5. Вернуть Result.retry(), если произошла временная системная ошибка.
6. Вернуть Result.failure(), только если ошибка явно непоправимая.
```

Основная логика Worker:

```kotlin
override suspend fun doWork(): Result {
    val startedAt = System.currentTimeMillis()
    backgroundCheckStatusRepository.saveRunStarted(startedAt)

    return try {
        val result = checkAndNotifyUseCase.execute()

        backgroundCheckStatusRepository.saveRunFinished(
            finishedAtMillis = System.currentTimeMillis(),
            state = result.monitorResult.checkResult.state,
            error = null,
            telegramSendResult = result.telegramSendResult,
            queueFlushResult = result.queueFlushResult
        )

        Result.success()
    } catch (exception: Exception) {
        backgroundCheckStatusRepository.saveRunFinished(
            finishedAtMillis = System.currentTimeMillis(),
            state = WhitelistState.UNKNOWN,
            error = exception.javaClass.simpleName,
            telegramSendResult = null,
            queueFlushResult = null
        )

        Result.retry()
    }
}
```

Если в проекте `CheckAndNotifyUseCase` называется иначе, используй существующее имя.

Важно:

```text
Worker не должен напрямую дублировать логику проверки.
Он должен использовать уже существующий use case.
```

Не надо копировать код из MainViewModel в Worker. Это прямой путь к двум разным приложениям внутри одного APK, прекрасная человеческая традиция.

## 8. BackgroundCheckScheduler

Создай класс:

```kotlin
class BackgroundCheckScheduler
```

Ответственность:

```text
1. Запланировать периодическую проверку.
2. Отменить периодическую проверку.
3. Перепланировать проверку при изменении интервала.
```

Использовать `WorkManager`.

Константы:

```kotlin
private const val UNIQUE_WORK_NAME = "whitelist_periodic_check"
```

Методы:

```kotlin
fun schedule(intervalMinutes: Long)

fun cancel()

fun reschedule(settings: BackgroundCheckSettings)
```

Логика `reschedule`:

```text
если settings.enabled == true:
    schedule(settings.normalizedIntervalMinutes)

если settings.enabled == false:
    cancel()
```

Периодическая работа:

```kotlin
val request = PeriodicWorkRequestBuilder<WhitelistCheckWorker>(
    intervalMinutes,
    TimeUnit.MINUTES
)
    .setConstraints(constraints)
    .build()
```

Constraints:

```kotlin
val constraints = Constraints.Builder()
    .setRequiredNetworkType(NetworkType.CONNECTED)
    .build()
```

Важно:

```text
NetworkType.CONNECTED не гарантирует cellular.
Это только условие запуска Worker.
Сама проверка всё равно должна внутри использовать CellularNetworkProvider и TRANSPORT_CELLULAR.
```

Запланировать:

```kotlin
workManager.enqueueUniquePeriodicWork(
    UNIQUE_WORK_NAME,
    ExistingPeriodicWorkPolicy.UPDATE,
    request
)
```

Если версия WorkManager не поддерживает `UPDATE`, используй:

```kotlin
ExistingPeriodicWorkPolicy.REPLACE
```

## 13. UX-тексты

Добавь пояснение:

```text
Фоновая проверка использует WorkManager. Android может сдвигать время запуска из-за энергосбережения. Для частых проверок нужен foreground service, но в MVP он не используется.
```

Добавь предупреждение:

```text
Telegram-уведомления по-прежнему отправляются только через указанный локальный proxy. Если proxy недоступен, сообщение сохраняется в очередь.
```

## 14. Как должна работать фоновая проверка

Цепочка Worker должна быть такой:

```text
WhitelistCheckWorker
    ↓
CheckAndNotifyUseCase
    ↓
TelegramQueueProcessor.flushQueue()
    ↓
WhitelistMonitorUseCase.checkAndUpdateState()
    ↓
WhitelistCheckUseCase
    ↓
CellularNetworkProvider
    ↓
MobileSiteChecker
    ↓
StateChangeDetector
    ↓
TelegramEventNotifierUseCase.notifyIfNeeded()
    ↓
TelegramNotifier через local proxy
    ↓
если ошибка, PendingTelegramReportRepository.save()
```

Worker не должен отдельно решать, что такое БС.  
Worker не должен отдельно форматировать Telegram.  
Worker не должен отдельно лезть в Room-очередь, кроме как через use case/repository.

## 15. Ошибки Worker

Если cellular-сеть недоступна, это не crash.

Такой результат должен пройти как обычный `NetworkCheckResult` со state:

```text
CELLULAR_NETWORK_UNAVAILABLE
```

и Worker должен вернуть:

```kotlin
Result.success()
```

Почему:

```text
Отсутствие cellular-сети — это результат проверки, а не падение приложения.
```

`Result.retry()` использовать только для непредвиденных исключений, например:

```text
ошибка инициализации зависимостей;
ошибка Room;
ошибка DataStore;
unexpected exception.
```

## 16. Не спамить Telegram

Старые правила остаются:

```text
Telegram отправляется только при подтверждённых событиях:
WHITELIST_TURNED_ON
WHITELIST_TURNED_OFF
```

Не отправлять:

```text
1. Каждую фоновую проверку.
2. Pending 1/2.
3. OTHER_CONFIRMED_CHANGE.
4. CELLULAR_NETWORK_UNAVAILABLE, если это не подтверждённый переход БС.
5. NO_MOBILE_INTERNET, если это не нужное событие.
```

Если WorkManager сделал 20 проверок за день, Telegram не должен получить 20 сообщений “ничего не изменилось”. Бот не виноват, что люди любят шум.

## 17. Очередь Telegram в фоне

Перед каждой фоновой проверкой нужно пытаться отправить очередь:

```text
1. Если proxy работает — старые сообщения уйдут.
2. Если proxy не работает — попытка обновит attemptCount/lastError.
3. Direct fallback всё ещё запрещён.
```

Сохрани поведение v0.5:

```text
Если первая отправка из очереди упала, не долбить остальные сообщения.
```

## 22. Acceptance criteria

После выполнения v0.6 должно работать так:

```text
1. Пользователь открывает приложение.
2. В секции "Автопроверка" включает автопроверку.
3. Выбирает интервал 15/30/60 минут.
4. Приложение сохраняет настройки.
5. Приложение планирует PeriodicWorkRequest через WorkManager.
6. Если пользователь выключает автопроверку, WorkManager-задача отменяется.
7. Если пользователь меняет интервал, задача перепланируется.
8. Worker выполняет ту же цепочку, что ручная проверка.
9. Worker проверяет сайты только через cellular Network.
10. Worker отправляет Telegram только через local proxy.
11. Worker сохраняет Telegram-сообщение в очередь при ошибке отправки.
12. Worker не отправляет Telegram при отсутствии события включения/выключения БС.
13. UI показывает время последней фоновой проверки.
14. UI показывает последний статус фоновой проверки.
15. UI показывает последнюю ошибку фоновой проверки, если она была.
16. Приложение продолжает поддерживать ручную проверку.
17. Ручная проверка и фоновая проверка используют одну и ту же бизнес-логику.
```

## 23. Ручные тестовые сценарии

Сценарий 1:

- новая задача имеет интервал 30 минут.

Сценарий 4:

Ожидаемо:
- выполняется CheckAndNotifyUseCase;

Telegram proxy выключен, есть событие БС.
Ожидаемо:

Нет изменений БС.

## 24. Требования к качеству

Обязательно:

```text
1. Проект должен компилироваться.
2. Не оставлять TODO вместо рабочей логики.
3. WorkManager должен использовать unique periodic work.
4. Нельзя создавать несколько одинаковых периодических задач.
5. Выключение автопроверки должно отменять задачу.
6. Изменение интервала должно перепланировать задачу.
7. Worker не должен дублировать бизнес-логику.
8. Worker должен использовать CheckAndNotifyUseCase.
9. Worker не должен использовать direct Telegram.
10. Worker не должен использовать activeNetwork для проверки сайтов.
11. Worker не должен использовать bindProcessToNetwork.
12. Cellular-сеть недоступна — это Result.success(), не crash.
13. Telegram proxy недоступен — это очередь, не direct fallback.
14. UI должен переживать null BackgroundCheckStatus.
15. UI должен переживать ошибки Worker.
16. DataStore должен безопасно читать пустые значения.
17. Room-очередь из v0.5 не должна сломаться.
18. Ручная проверка должна работать как раньше.
```
