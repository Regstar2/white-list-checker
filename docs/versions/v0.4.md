# Cursor prompt: Whitelist Checker Android MVP v0.4

Доработай Android-приложение Whitelist Checker с версии v0.3 до v0.4.

Главная цель v0.4: добавить отправку Telegram-уведомлений через Telegram Bot API, но строго через заданный пользователем локальный HTTP/SOCKS-прокси.

Приложение должно отправлять Telegram-сообщение только при подтверждённом событии включения или выключения белых списков:

```text
WHITELIST_OFF → WHITELIST_ON
WHITELIST_ON → WHITELIST_OFF
```

Прямой доступ к Telegram API запрещён. Если прокси недоступен, приложение не должно пытаться отправить сообщение напрямую. Никаких “попробуем без прокси”, это не оптимизм, это баг с улыбкой.

## 2. Цель v0.4

Приложение должно:

```text
1. Иметь экран/секцию настроек Telegram.
2. Хранить:
   - bot token;
   - chat id;
   - proxy type;
   - proxy host;
   - proxy port.
3. Поддерживать proxy type:
   - HTTP;
   - SOCKS.
4. Проверять связь с Telegram через proxy методом getMe.
5. Отправлять Telegram-сообщение через proxy методом sendMessage.
6. Никогда не отправлять Telegram-запросы напрямую.
7. Отправлять уведомление только при подтверждённых событиях:
   - WHITELIST_TURNED_ON;
   - WHITELIST_TURNED_OFF.
8. Не отправлять уведомления для:
   - OTHER_CONFIRMED_CHANGE;
   - NO_CONFIRMED_CHANGE;
   - одиночных pending-состояний 1/2.
9. Показывать в UI статус Telegram:
   - настроен / не настроен;
   - proxy проверен / ошибка;
   - последнее сообщение отправлено / ошибка отправки.
10. Не добавлять WorkManager.
11. Не добавлять Room.
12. Не добавлять очередь неотправленных сообщений.
13. Не добавлять управление приложением через Telegram-команды.
```

Очередь неотправленных сообщений будет отдельной версией v0.5. Сейчас при ошибке отправки нужно только показать ошибку пользователю.

## 5. Telegram API

Использовать Telegram Bot API:

```text
getMe:
GET или POST https://api.telegram.org/bot<TOKEN>/getMe

sendMessage:
POST https://api.telegram.org/bot<TOKEN>/sendMessage
```

Все запросы должны идти через заданный локальный proxy.

Прямой запрос запрещён.

Правильная схема:

```text
Android-приложение
    ↓
OkHttpClient с Proxy
    ↓
127.0.0.1:<port>
    ↓
Telegram Bot API
```

Неправильная схема:

```text
proxy не сработал
    ↓
попробовать напрямую
```

Так делать нельзя.

`TelegramProxyType` хранить как `String`, через `name`.

Парсить безопасно:

```kotlin
private fun parseProxyType(value: String?): TelegramProxyType {
    if (value.isNullOrBlank()) {
        return TelegramProxyType.SOCKS
    }

    return runCatching {
        TelegramProxyType.valueOf(value)
    }.getOrDefault(TelegramProxyType.SOCKS)
}
```

## 8. TelegramHttpClientFactory

Создай класс:

```kotlin
class TelegramHttpClientFactory
```

Метод:

```kotlin
fun create(settings: TelegramSettings): OkHttpClient
```

Он должен:

```text
1. Создать OkHttpClient.
2. Настроить Proxy.
3. Использовать HTTP или SOCKS в зависимости от settings.proxyType.
4. Настроить таймауты.
5. Запретить retryOnConnectionFailure.
6. Не создавать client без proxy.
```

Таймауты:

```kotlin
connectTimeout = 8 секунд
readTimeout = 8 секунд
callTimeout = 12 секунд
```

Пример логики:

```kotlin
val proxyType = when (settings.proxyType) {
    TelegramProxyType.HTTP -> Proxy.Type.HTTP
    TelegramProxyType.SOCKS -> Proxy.Type.SOCKS
}

val proxy = Proxy(
    proxyType,
    InetSocketAddress(settings.proxyHost, settings.proxyPort)
)

return OkHttpClient.Builder()
    .proxy(proxy)
    .connectTimeout(8, TimeUnit.SECONDS)
    .readTimeout(8, TimeUnit.SECONDS)
    .callTimeout(12, TimeUnit.SECONDS)
    .retryOnConnectionFailure(false)
    .build()
```

Важно:

```text
Даже если settings некорректные, не создавай direct client.
Лучше вернуть ошибку выше по стеку.
```

## 10. testConnection

`testConnection(settings)` должен:

```text
1. Проверить settings.isConfigured.
2. Если настройки неполные, вернуть Failure.
3. Создать OkHttpClient через TelegramHttpClientFactory.
4. Вызвать:
   https://api.telegram.org/bot<TOKEN>/getMe
5. Вернуть Success, если HTTP 200 и тело ответа похоже на успешный Telegram JSON.
6. Вернуть Failure с причиной, если:
   - proxy недоступен;
   - token неверный;
   - Telegram API недоступен через proxy;
   - произошла IOException;
   - получен неуспешный HTTP-код.
```

Пример проверки:

```text
HTTP 200 → Success
HTTP 401 → Failure("Неверный bot token")
HTTP 407 → Failure("Proxy требует авторизацию или отклонил запрос")
остальное → Failure("HTTP <code>")
IOException → Failure("<ExceptionName>")
```

Не нужно подключать JSON-библиотеку только ради `getMe`. Можно проверить HTTP-код. Если в проекте уже есть kotlinx.serialization, можно распарсить аккуратно, но не тащи новую зависимость ради одного bool, пожалуйста.

## 11. sendMessage

`sendMessage(settings, text)` должен:

```text
1. Проверить settings.isConfigured.
2. Если настройки неполные, вернуть Failure.
3. Создать OkHttpClient через TelegramHttpClientFactory.
4. Сделать POST на:
   https://api.telegram.org/bot<TOKEN>/sendMessage
5. Передать параметры:
   - chat_id;
   - text;
   - parse_mode = HTML;
   - disable_web_page_preview = true.
6. Вернуть Success при успешном HTTP 200.
7. Вернуть Failure при ошибке.
```

Тело запроса через `FormBody`:

```kotlin
val body = FormBody.Builder()
    .add("chat_id", settings.chatId)
    .add("text", text)
    .add("parse_mode", "HTML")
    .add("disable_web_page_preview", "true")
    .build()
```

## 13. Когда отправлять Telegram

После выполнения проверки в `WhitelistMonitorUseCase` или в отдельном use case нужно отправлять Telegram только если:

```kotlin
event.type == WhitelistStateChangeType.WHITELIST_TURNED_ON
        || event.type == WhitelistStateChangeType.WHITELIST_TURNED_OFF
```

Не отправлять для:

```text
OTHER_CONFIRMED_CHANGE
NO_CONFIRMED_CHANGE
pendingStateCount = 1
начальной фиксации UNKNOWN → WHITELIST_OFF/ON
```

## 14. Создать TelegramEventNotifierUseCase

Лучше создать отдельный use case:

```kotlin
class TelegramEventNotifierUseCase
```

Зависимости:

```text
TelegramSettingsRepository
TelegramNotifier
TelegramReportFormatter
```

Метод:

```kotlin
suspend fun notifyIfNeeded(
    event: WhitelistStateChangeEvent?,
    checkResult: NetworkCheckResult
): TelegramSendResult?
```

Логика:

```text
1. Если event == null → вернуть null.
2. Если event.type не WHITELIST_TURNED_ON и не WHITELIST_TURNED_OFF → вернуть null.
3. Получить TelegramSettings.
4. Если settings.isConfigured == false → вернуть Failure("Telegram не настроен").
5. Сформировать текст через TelegramReportFormatter.
6. Отправить через TelegramNotifier.sendMessage.
7. Вернуть результат.
```

## 22. Важный security-минимум

В v0.4 можно хранить bot token в DataStore как обычную строку, потому что это MVP.

Но:

```text
1. Не логировать bot token.
2. Не показывать полный bot token в UI после сохранения.
3. В поле ввода использовать password visual transformation или хотя бы скрывать токен частично.
4. Не добавлять token в exception message.
5. Не писать token в Logcat.
```

Если есть логирование запросов OkHttp — не подключать его для Telegram.

## 23. Правила Telegram direct запрещён

Проверь код на такие ошибки:

```text
1. Не должно быть второго OkHttpClient без proxy для Telegram.
2. Не должно быть fallback direct.
3. Не должно быть URL.openConnection для Telegram.
4. Не должно быть попытки использовать activeNetwork для Telegram.
5. Не должно быть bindProcessToNetwork для Telegram.
```

Для Telegram всегда:

```text
OkHttpClient.Builder()
    .proxy(proxy)
```

Если настройки proxy невалидные:

```text
вернуть Failure
```

а не:

```text
создать direct client
```

## 27. Acceptance criteria

После выполнения v0.4 должно работать так:

```text
1. Пользователь открывает приложение.
2. Пользователь вводит:
   - bot token;
   - chat id;
   - proxy type;
   - proxy host;
   - proxy port.
3. Пользователь нажимает "Сохранить настройки".
4. Пользователь нажимает "Проверить связь с Telegram".
5. Приложение вызывает getMe через указанный proxy.
6. Если proxy/token рабочие, UI показывает успешный тест.
7. Пользователь выполняет проверки мобильной сети.
8. Если состояние БС не изменилось подтверждённо, Telegram не отправляется.
9. Если есть только pending 1/2, Telegram не отправляется.
10. Если подтверждён переход WHITELIST_OFF → WHITELIST_ON:
    - приложение формирует сообщение "Белые списки включились";
    - отправляет его через proxy;
    - показывает результат отправки в UI.
11. Если подтверждён переход WHITELIST_ON → WHITELIST_OFF:
    - приложение формирует сообщение "Белые списки выключились";
    - отправляет его через proxy;
    - показывает результат отправки в UI.
12. Если proxy недоступен:
    - сообщение не отправляется;
    - direct fallback не используется;
    - UI показывает ошибку.
13. Приложение продолжает проверять сайты только через cellular Network.
14. Telegram отправляется только через OkHttpClient с proxy.
```

## 28. Тестовые сценарии вручную

```text

Telegram settings пустые.

Bot token неправильный.
Proxy рабочий.
Нажать "Проверить связь".

Proxy port неправильный.
Нажать "Проверить связь".
Ожидаемо: ошибка подключения, direct fallback отсутствует.

Сценарий 4:
Proxy рабочий, token рабочий.
Нажать "Проверить связь".
Ожидаемо: Success.

Сценарий 5:
Есть событие WHITELIST_TURNED_ON.
Telegram настроен.
Ожидаемо: сообщение отправлено.

Сценарий 6:
Есть событие OTHER_CONFIRMED_CHANGE.
Ожидаемо: Telegram не отправляется.

Сценарий 7:
Есть pendingStateCount = 1.
Ожидаемо: Telegram не отправляется.
```
