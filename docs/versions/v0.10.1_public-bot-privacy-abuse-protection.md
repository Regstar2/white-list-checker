## Архитектурный принцип

Privacy и abuse checks должны быть отдельными policy/filter компонентами, а не случайными if внутри каждого handler.

## Требования к реализации

- Privacy filter удаляет installationId, raw device data, точные координаты, private diagnostics, internal errors.
- Minimum thresholds: минимум N reports, N independent sources, max age, minimum confidence.
- Если threshold не пройден — `INSUFFICIENT_DATA`, без подробностей.
- Abuse events: RATE_LIMITED, BLOCKED_USER_REQUEST, ADMIN_COMMAND_ATTEMPT, ENUMERATION_PATTERN, INVALID_COMMAND_SPAM, PRIVACY_FILTER_TRIGGERED.
- Safe errors не показывают stack trace, SQL errors, Worker internals, secrets.

## Приватность и безопасность

Запрещено сохранять, показывать, отправлять или логировать:

- номер телефона;
- IMEI;
- IMSI;
- точные координаты;
- токены;
- bot token;
- shared secret;
- authorization headers;
- приватные URL и query-параметры с секретами;
- raw reports там, где пользователь должен видеть только агрегаты.

Если поле сомнительное — не включай его в публичный/серверный контракт без явного обоснования.

## Тесты

Добавь или обнови тесты, если инфраструктура проекта позволяет:

1. Public response не содержит installationId/raw reports.
2. Один источник → INSUFFICIENT_DATA.
3. Мало отчётов → INSUFFICIENT_DATA.
4. Старые данные → STALE/INSUFFICIENT_DATA.
5. Low confidence скрывается.
6. Admin diagnostics недоступна public user.
7. Rate limit срабатывает.
8. Blocked user не получает данные.
9. Enumeration pattern логируется.
10. Internal error не показывает stack trace.
11. Privacy filter ограничивает длинные списки.

Если тесты добавить невозможно без большого рефакторинга:

1. Не тащи новый тяжёлый тестовый стек.
2. Честно укажи это в отчёте.
3. Добавь подробный ручной сценарий проверки.
4. Сохрани код так, чтобы его можно было протестировать позже.
