# Cursor prompt: Whitelist Checker Android MVP v0.3.5

Доработай Android-приложение Whitelist Checker с версии v0.3 до v0.3.5.

Главная цель v0.3.5: добавить локальные Android-уведомления при подтверждённом включении или выключении белых списков.

Важно: это промежуточная версия между v0.3 и Telegram-интеграцией. Telegram, proxy, очередь Telegram и WorkManager пока НЕ добавлять.

Приложение уже умеет вручную проверять мобильную сеть, определять состояние БС и через антидребезг создавать событие смены состояния. Теперь нужно добавить локальный канал уведомлений на устройстве.

```text
   - WHITELIST_OFF
```

## 2. Цель v0.3.5

Приложение должно:

```text
1. Иметь настройку "Локальные уведомления включены".
2. Хранить эту настройку в DataStore.
3. Запрашивать разрешение POST_NOTIFICATIONS на Android 13+.
4. Создавать notification channel для Android 8+.
5. Отправлять локальное уведомление только при подтверждённых событиях:
   - WHITELIST_TURNED_ON;
   - WHITELIST_TURNED_OFF.
6. Не отправлять уведомления для:
   - OTHER_CONFIRMED_CHANGE;
   - pendingStateCount = 1;
   - начальной фиксации UNKNOWN;
   - обычных проверок без смены БС.
7. Показывать в UI:
   - включены ли локальные уведомления;
   - выдано ли разрешение на уведомления;
   - результат последней попытки локального уведомления.
8. Не добавлять Telegram.
9. Не добавлять proxy.
10. Не добавлять очередь сообщений.
11. Не добавлять WorkManager.
12. Не добавлять Android foreground service.
```

## 3. Android permissions

В `AndroidManifest.xml` добавь разрешение:

```xml
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
```

Разрешение нужно только для Android 13+.

На Android ниже 13 runtime-запрос не нужен, но notification channel всё равно нужен для Android 8+.

Убедись, что уже есть старые разрешения из v0.1-v0.3:

```xml
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />
<uses-permission android:name="android.permission.CHANGE_NETWORK_STATE" />
```

## 12. LocalNotificationSender

Создай класс:

```kotlin
class LocalNotificationSender
```

Зависимости:

```text
Context
LocalNotificationChannelManager
LocalNotificationPermissionChecker
LocalNotificationFormatter
```

Метод:

```kotlin
fun sendStateChangeNotification(
    event: WhitelistStateChangeEvent,
    checkResult: NetworkCheckResult
): LocalNotificationResult
```

Логика:

```text
1. Если event.type не WHITELIST_TURNED_ON и не WHITELIST_TURNED_OFF:
   - вернуть Disabled или Failure не надо;
   - лучше вернуть Disabled или отдельный результат не нужен, потому что метод не должен вызываться для этих событий.
2. Проверить, разрешены ли уведомления.
3. Если уведомления не разрешены:
   - вернуть PermissionNotGranted.
4. Создать notification channel через LocalNotificationChannelManager.
5. Сформировать title/text.
6. Создать NotificationCompat.Builder.
7. Отправить через NotificationManagerCompat.notify(...).
8. Вернуть Success.
9. Если произошла ошибка, вернуть Failure.
```

Notification ID:

```kotlin
private const val WHITELIST_TURNED_ON_NOTIFICATION_ID = 1001
private const val WHITELIST_TURNED_OFF_NOTIFICATION_ID = 1002
```

Можно использовать разные ID, чтобы уведомления включения/выключения не затирали друг друга.  
Если хочешь затирать старое уведомление новым — используй один ID. Для MVP лучше разные ID.

Notification builder:

```kotlin
NotificationCompat.Builder(context, WHITELIST_EVENTS_CHANNEL_ID)
    .setSmallIcon(R.drawable.ic_stat_whitelist)
    .setContentTitle(title)
    .setContentText(text)
    .setStyle(NotificationCompat.BigTextStyle().bigText(text))
    .setPriority(NotificationCompat.PRIORITY_DEFAULT)
    .setAutoCancel(true)
```

Если `R.drawable.ic_stat_whitelist` ещё нет, создай простой vector drawable для small icon.  
Small icon должен быть монохромным/простым, подходящим для status bar. Не используй launcher icon как small notification icon, это часто выглядит как визуальная авария.

Создай файл:

```text
app/src/main/res/drawable/ic_stat_whitelist.xml
```

Простой vector icon, например щит/галочка/сигнал. Без сложных цветов.

## 13. LocalNotificationEventUseCase

Создай use case:

```kotlin
class LocalNotificationEventUseCase
```

Зависимости:

```text
LocalNotificationSettingsRepository
LocalNotificationSender
```

Метод:

```kotlin
suspend fun notifyIfNeeded(
    event: WhitelistStateChangeEvent?,
    checkResult: NetworkCheckResult
): LocalNotificationResult?
```

Логика:

```text
1. Если event == null:
   - return null.
2. Если event.type не WHITELIST_TURNED_ON и не WHITELIST_TURNED_OFF:
   - return null.
3. Получить LocalNotificationSettings.
4. Если settings.enabled == false:
   - return LocalNotificationResult.Disabled.
5. Вызвать LocalNotificationSender.sendStateChangeNotification(event, checkResult).
6. Вернуть результат.
```

Важно:

```text
Pending-состояния 1/2 не должны вызывать локальные уведомления.
Начальная фиксация UNKNOWN не должна вызывать локальные уведомления.
OTHER_CONFIRMED_CHANGE не должен вызывать локальные уведомления.
```

## 14. Обновить верхнеуровневый use case

Если после v0.3 у тебя есть только:

```kotlin

```

то создай новый use case:

```kotlin

```

Он должен делать:

```text
1. Выполнить WhitelistMonitorUseCase.checkAndUpdateState().
2. Получить event.
3. Если event подходит, вызвать LocalNotificationEventUseCase.notifyIfNeeded(...).
4. Вернуть общий результат для UI.
```

Добавь модель:

```kotlin
data class CheckAndLocalNotifyResult(
    val monitorResult: WhitelistMonitorResult,
    val localNotificationResult: LocalNotificationResult?
)
```

Если в проекте уже есть будущий `CheckAndNotifyUseCase`, можно использовать имя:

```kotlin
CheckAndNotifyUseCase
```

Но в v0.3.5 внутри него должен быть только local notification канал. Telegram пока не добавлять.

Рекомендуемая структура:

```text
WhitelistMonitorUseCase:
    только проверка + антидребезг + event.

LocalNotificationEventUseCase:
    только локальное уведомление.

CheckAndLocalNotifyUseCase:
    связывает мониторинг и локальное уведомление.
```

Не пихай отправку уведомления прямо внутрь `StateChangeDetector`. Детектор должен считать события, а не трясти NotificationManager.

Правила обязательны:

```text

3. Не отправлять уведомление при начальной фиксации UNKNOWN.
4. Не отправлять уведомление при OTHER_CONFIRMED_CHANGE.
5. Не отправлять уведомление при NO_MOBILE_INTERNET, если это не переход WHITELIST_ON/OFF.
6. Отправлять только при:
   - WHITELIST_TURNED_ON;
   - WHITELIST_TURNED_OFF.
```

## 23. Acceptance criteria

После выполнения v0.3.5 должно работать так:

```text
1. Пользователь открывает приложение.
2. Приложение создаёт notification channel.
3. В UI есть секция "Локальные уведомления".
4. Пользователь может включить/выключить локальные уведомления.
5. На Android 13+ пользователь может нажать "Разрешить уведомления".
6. Приложение показывает, выдано ли разрешение.
7. Пользователь запускает ручную проверку.
8. Если подтверждённого события БС нет, локальное уведомление не отправляется.
9. Если есть pendingStateCount = 1, локальное уведомление не отправляется.
10. Если подтверждён переход WHITELIST_OFF → WHITELIST_ON, приложение показывает локальное уведомление "Белые списки включились".
11. Если подтверждён переход WHITELIST_ON → WHITELIST_OFF, приложение показывает локальное уведомление "Белые списки выключились".
12. Если локальные уведомления выключены, уведомление не отправляется.
```

## 25. Требования к качеству

