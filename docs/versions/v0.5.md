# Cursor prompt: Whitelist Checker Android MVP v0.5

Доработай Android-приложение Whitelist Checker с версии v0.4 до v0.5.

Главная цель v0.5: добавить очередь неотправленных Telegram-уведомлений.

После v0.4 приложение уже умеет отправлять Telegram-сообщения через локальный HTTP/SOCKS-прокси при подтверждённом включении/выключении белых списков. Но если прокси временно недоступен, Telegram API не отвечает, токен неверный или сеть решила сыграть в “я работаю, но нет”, событие сейчас может быть потеряно.

В v0.5 нужно сделать так, чтобы важные Telegram-уведомления не терялись. Если отправка не удалась, сообщение сохраняется локально и приложение пробует отправить его позже.

Прямой доступ к Telegram по-прежнему запрещён. Telegram API вызывается только через заданный локальный proxy. Никакого direct fallback. Это не “надёжность”, это самообман с HTTP-кодами.

## 3. Хранилище очереди

В v0.5 нужно добавить Room.

Почему Room:

```text
1. Очередь может содержать несколько сообщений.
2. Нужно хранить attemptCount.
3. Нужно хранить lastError.
4. Нужно удалять старые записи.
```

DataStore оставить для настроек и мониторинга состояния.

Room использовать только для очереди Telegram-сообщений.

Создай repository:

Ограничения:


```text

```

Лучше в v0.5 сделать так:

```text
- старше 7 дней удалять;
- больше 20 сообщений — удалять самые старые;
- attemptCount >= 10 — не отправлять автоматически, но показывать в UI как зависшие.
```

## 10. TelegramQueueProcessor

Создай use case:

```kotlin
class TelegramQueueProcessor
```

Зависимости:

```text
PendingTelegramReportRepository
TelegramSettingsRepository
TelegramNotifier
```

Метод:

```kotlin
suspend fun flushQueue(): TelegramQueueFlushResult
```

Модель результата:

```kotlin
data class TelegramQueueFlushResult(
    val attemptedCount: Int,
    val sentCount: Int,
    val failedCount: Int,
    val skippedCount: Int,
    val lastError: String?
)
```

Алгоритм:

```text
1. Получить TelegramSettings.
2. Если Telegram не настроен:
   - вернуть result с skippedCount = count очереди;
   - ничего не отправлять.
3. Удалить старые отчёты старше 7 дней.
4. Получить список pending reports.
5. Отфильтровать сообщения с attemptCount < MAX_ATTEMPT_COUNT.
6. Отправлять сообщения по очереди, от старых к новым.
7. Для каждого сообщения:
   - вызвать TelegramNotifier.sendMessage(settings, text);
   - если Success:
       удалить сообщение из очереди;
   - если Failure:
       увеличить attemptCount;
       записать lastAttemptAtMillis;
       записать lastError;
       продолжить со следующим или остановиться.
```

В v0.5 лучше остановиться после первой ошибки отправки.

Почему:

```text
Если proxy умер, нет смысла долбить остальные 19 сообщений подряд.
Это не очередь, это DDoS самого себя через localhost.
```

То есть логика:

```text
Success → удалить и идти дальше.
Failure → обновить attempt и остановить flush.
```

## 11. Обновить TelegramEventNotifierUseCase

Сейчас в v0.4 он, вероятно, делает:

```text
сформировать сообщение
↓
отправить через TelegramNotifier
↓
вернуть TelegramSendResult
```

В v0.5 нужно изменить поведение:

```text
сформировать сообщение
↓
попробовать отправить
↓
если Success:
    вернуть Success
↓
если Failure:
    сохранить сообщение в PendingTelegramReportRepository
    вернуть Failure
```

Метод:

```kotlin
suspend fun notifyIfNeeded(
    event: WhitelistStateChangeEvent?,
    checkResult: NetworkCheckResult
): TelegramSendResult?
```

Логика:

```text
1. Если event == null → return null.
2. Если event.type не WHITELIST_TURNED_ON и не WHITELIST_TURNED_OFF → return null.
3. Получить настройки Telegram.
4. Сформировать text.
5. Если Telegram не настроен:
   - сохранить text в очередь с error = "Telegram не настроен";
   - вернуть Failure.
6. Попробовать отправить.
7. Если Success → вернуть Success.
8. Если Failure:
   - сохранить text в очередь;
   - вернуть Failure.
```

Важно:

```text
Не сохранять дубликаты одного и того же события бесконечно.
```

Чтобы избежать дублей, можно добавить `id` как deterministic:

```text
id = "${event.type}_${event.changedAtMillis}"
```

Тогда `OnConflictStrategy.REPLACE` не даст плодить один и тот же отчёт при повторном проходе.

## 12. Обновить CheckAndNotifyUseCase

В v0.5 `CheckAndNotifyUseCase` должен:

```text
1. Сначала попробовать отправить старую очередь.
2. Потом выполнить новую проверку.
3. Потом, если возникло новое событие БС, отправить или сохранить новое Telegram-сообщение.
4. Вернуть общий результат.
```

Почему сначала очередь:

```text
Если старые события уже лежат, их нужно отправить до новых, чтобы порядок был нормальным.
```

Обнови модель результата:

```kotlin
data class CheckAndNotifyResult(
    val monitorResult: WhitelistMonitorResult,
    val telegramSendResult: TelegramSendResult?,
    val queueFlushResult: TelegramQueueFlushResult?,
    val pendingReportsCount: Int
)
```

Алгоритм:

```text
1. queueFlushResult = telegramQueueProcessor.flushQueue()
2. monitorResult = whitelistMonitorUseCase.checkAndUpdateState()
3. telegramSendResult = telegramEventNotifierUseCase.notifyIfNeeded(
       event = monitorResult.stateChangeEvent,
       checkResult = monitorResult.checkResult
   )
4. pendingReportsCount = pendingTelegramReportRepository.count()
5. return CheckAndNotifyResult(...)
```

Если flushQueue упал непредвиденно, не надо ломать сетевую проверку.  
Обработай ошибку как failure result, но проверку БС всё равно выполни.

```text

```

## 23. Acceptance criteria

После выполнения v0.5 должно работать так:

```text
1. Пользователь настроил Telegram bot token, chat id и proxy.
2. Приложение проверяет связь с Telegram через proxy.
3. Если при событии БС сообщение отправилось успешно:
   - очередь остаётся пустой.
4. Если при событии БС отправка не удалась:
   - сообщение сохраняется в Room-очередь.
5. UI показывает количество неотправленных сообщений.
6. Пользователь нажимает "Повторить отправку очереди".
7. Приложение пытается отправить старые сообщения через proxy.
8. Если отправка успешна:
   - сообщение удаляется из очереди.
9. Если отправка снова неуспешна:
   - attemptCount увеличивается;
   - lastAttemptAtMillis обновляется;
   - lastError обновляется.
10. Перед каждой новой ручной проверкой приложение пробует отправить старую очередь.
11. Прямой Telegram-запрос не используется вообще.
12. Сетевые проверки сайтов по-прежнему идут только через cellular Network.
13. Telegram по-прежнему идёт только через local proxy.
```

## 24. Ручные тестовые сценарии

Проверь вручную:

```text
Сценарий 1:
Telegram не настроен.
Создать событие WHITELIST_TURNED_ON.
Ожидаемо:
- сообщение не отправлено;
- сообщение сохранено в очередь;
- UI показывает pendingReportsCount = 1.

Сценарий 2:
Telegram настроен, proxy выключен.
Создать событие WHITELIST_TURNED_ON.
Ожидаемо:
- sendMessage возвращает Failure;
- сообщение сохранено в очередь;
- direct fallback отсутствует.

Сценарий 3:
Включить proxy.
Нажать "Повторить отправку очереди".
Ожидаемо:
- сообщение отправлено;
- запись удалена из очереди;
- pendingReportsCount = 0.

Сценарий 4:
В очереди 3 сообщения, proxy рабочий.
Нажать flush.
Ожидаемо:
- сообщения отправляются от старых к новым;
- успешные удаляются.

Сценарий 5:
В очереди 3 сообщения, proxy умер на первом.
Ожидаемо:
- первая попытка получает Failure;
- attemptCount первой записи увеличен;
- остальные не долбятся зря;
- flush останавливается.

Сценарий 6:
pendingStateCount = 1.
Ожидаемо:
- Telegram не отправляется;
- очередь не пополняется.

Сценарий 7:
OTHER_CONFIRMED_CHANGE.
Ожидаемо:
- Telegram не отправляется;
- очередь не пополняется.
```

## 25. Требования к качеству

Обязательно:

```text
1. Проект должен компилироваться.
2. Не оставлять TODO вместо рабочей логики.
3. Room database должна инициализироваться без крашей.
4. Очередь должна сохраняться между перезапусками приложения.
5. Успешно отправленные сообщения должны удаляться.
6. Неуспешные попытки должны обновлять attemptCount и lastError.
7. Старые сообщения должны удаляться по лимиту возраста.
8. Очередь должна ограничиваться по размеру.
9. Telegram direct fallback запрещён.
10. Telegram token не логировать.
11. Telegram token не сохранять в Room.
12. Сетевые проверки сайтов не ломать.
13. Не использовать bindProcessToNetwork.
14. Не использовать activeNetwork для проверки сайтов.
15. Не блокировать main thread.
16. UI должен переживать пустую очередь.
17. UI должен переживать ошибки flush.
18. UI должен переживать невалидные Telegram-настройки.
```

## 26. Финальная задача

Доработай проект до v0.5.

```text
Проверка мобильной сети
    ↓

    ↓
Антидребезг 2 проверки подряд
    ↓
Событие включения/выключения БС
    ↓
```

```text
Telegram send failed
    ↓
Save to Room queue
    ↓
Retry later через тот же local proxy
    ↓
On success delete from queue
```
