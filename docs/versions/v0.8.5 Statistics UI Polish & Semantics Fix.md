## Контекст

После v0.8.4 экран статистики начал показывать статистику проверок и статистику белых списков, но текущий UI выглядит сыро и местами вводит в заблуждение.

По текущим скриншотам видно несколько проблем:

1. Экран статистики перегружен длинными карточками.
2. Много одинаковых строк без визуальной иерархии.
3. Графики выглядят как обычные progress bars и плохо объясняют данные.
4. Бар “Доступность по дням” показывает значение 90 без знака процента.
5. “Топ нестабильных targets” показывает всем targets значение 1, из-за чего все бары заполнены на 100% и выглядят бессмысленно.
6. “Топ targets по доступности” показывает 100 без знака процента.
7. Смешаны английские и русские подписи: “targets”, “Endpoints”, “target”.
8. В endpoint-блоке показываются сырые URL, что визуально засоряет экран и может быть проблемой приватности.
9. На главном экране есть противоречие: статус проверки “успешно”, но статистика показывает “Успешность 0%” и “Серия ошибок 241”.
10. Статистика проверок путает техническую успешность запуска проверки и факт обнаружения whitelist.
11. Главный экран показывает “Белые списки не обнаружены”, но экран статистики показывает “Сейчас доступно 6”, что выглядит противоречиво.
12. Карточки слишком крупные, экран плохо сканируется глазами.
13. Не хватает компактного summary сверху.
14. Не хватает нормальных empty/insufficient-data состояний для графиков.
15. Не хватает единых правил форматирования процентов, дат, миллисекунд и неизвестных значений.

Эта версия должна не добавлять новую аналитику, а привести уже добавленную статистику в понятный, аккуратный и непротиворечивый вид.

## Главная цель версии

Исправить смысловые ошибки и визуальное отображение статистики.

После реализации:

- главный экран не должен противоречить экрану статистики;
- статистика проверок и статистика белых списков должны быть визуально и семантически разделены;
- графики должны выглядеть осмысленно даже при малом количестве данных;

- экран статистики должен быть компактнее, чище и понятнее.

## Главный semantic fix

Нужно явно разделить четыре понятия:

### 1. Technical check status

Это статус запуска проверки:

- проверка завершилась;
- проверка была отменена;
- проверка упала;
- часть targets не удалось проверить;
- storage/network error.

Примеры UI:

- “Проверка завершена”.
- “Проверка завершена частично”.
- “Проверка завершилась с ошибкой”.
- “Проверка отменена”.

### 2. Whitelist detection result

Это итог по смыслу приложения:

- признаки whitelist обнаружены;
- признаки whitelist не обнаружены;
- недостаточно данных;
- результат неизвестен.

Примеры UI:

- “Признаки whitelist обнаружены”.
- “Признаки whitelist не обнаружены”.
- “Недостаточно данных для вывода”.
- “Результат неизвестен”.

### 3. Target availability

Это доступность отдельных целей:

- target доступен;
- target недоступен;
- target unknown/error.

Примеры UI:

- “Доступные цели”.
- “Недоступные цели”.
- “Неизвестно”.

### 4. Endpoint/check statistics

Это техническая статистика по проверкам:

- всего проверок;
- успешных target checks;
- ошибочных target checks;
- средняя задержка;
- последняя ошибка.

Нельзя называть target availability “успешностью проверок”, если это не одно и то же.

## Исправить противоречия на главном экране

Сейчас главный экран может показывать:

- “Статус: успешно”;
- “Белые списки не обнаружены”;
- “Внешние 3/4, локальные 3/4”;
- “Успешность 0%”;
- “Серия ошибок 241”.

Это выглядит как баг.

Требования:

1. Если проверка технически завершилась, но whitelist не обнаружен, писать:
   - technical status: “Проверка завершена”;
   - detection result: “Признаки whitelist не обнаружены”.
2. Не использовать слово “успешно” для технического статуса, если оно конфликтует с successRate.
3. Если 225 из 241 проверок частично успешны, не показывать “Серия ошибок 241” без объяснения.
4. Серия ошибок должна считаться только по полностью ошибочным check runs, если domain-логика это подразумевает.
5. Если partial success не является failure, не увеличивать consecutiveFailureCount.
6. Если successRate считает только полностью успешные runs, переименовать UI label:
   - не “Успешность”;
   - а “Полностью успешные проверки”.
7. Если нужен общий health-rate, использовать отдельную модель/label, но не добавлять новую сложную метрику без необходимости.
8. На главном экране показывать только 3–5 ключевых значений, остальное оставить на экране статистики.

## Рекомендуемая новая структура главной карточки статистики

На главном экране в карточке “Статистика” показывать компактно:

- Проверок: 241.
- Завершено без ошибок: X%.
- Частично завершено: Y.
- Последняя проверка: только что.
- Ошибок подряд: N.

Если “Ошибок подряд” = 0, можно скрыть строку или показать “Нет”.

Не показывать на главном экране слишком много технических деталей.

## Рекомендуемая структура экрана статистики

Экран “Статистика” сделать так:

1. Summary header.
2. Кратко: проверки.
3. Кратко: белые списки / доступность.
4. Графики.
5. Targets.
6. Endpoints details — свернутый блок или отдельная секция ниже.
7. Diagnostics/debug — только если уже есть.

## Summary header

Верхняя карточка должна быть полезнее, чем просто “Данные обновлены только что”.

Показать:

- “Обновлено: только что”.
- “Последняя проверка: завершена / частично / ошибка”.
- “Период данных: сегодня / 7 дней / 30 дней / всё время”, если период уже есть.
- Если данных мало: “Данных пока мало”.

Не делать большую пустую карточку.

## Карточка “Проверки”

Переименовать “Общая статистика” в “Проверки”, если это техническая статистика.

Показать компактно:

- Всего проверок.
- Завершено без ошибок.
- Частично завершено.
- С ошибкой.
- Средняя задержка.
- Последняя проверка.
- Ошибок подряд.

Требования:

1. Не показывать “Последняя успешная: Нет данных”, если это выглядит бесполезно. Можно скрывать строку или показывать только при наличии.
2. Не показывать “Последняя ошибка: только что”, если текущий run был partial success и это не полная ошибка.
3. Если successRate = 0 из-за строгой логики “полностью успешные”, подписать это явно:
   - “Полностью успешные”.
4. Не использовать слишком длинные строки в двухколоночном layout, если они переносятся некрасиво.

## Карточка “Белые списки”

Переименовать или уточнить блок “Статистика белых списков”, если данные на самом деле про доступность targets.

Возможные названия:

- “Доступность целей”.
- “Белые списки”.
- “Состояние targets”.

Выбрать по фактическому смыслу domain-модели.

Показать:

- Доступно.
- Недоступно.
- Неизвестно.
- Доступность.
- Включений.
- Выключений.
- Последнее включение.
- Последнее выключение.
- Самый нестабильный target.

Требования:

1. Процент показывать как `85.7%`, не `85.7`.
2. Если включений/выключений мало, добавить пояснение “за выбранный период” или “за всё время”.
3. Если “самый нестабильный target” имеет такой же score, как остальные, не выделять его как однозначно худший. Можно показать “Недостаточно данных”.
4. Если все targets имеют unstableScore = 1, топ нестабильных не должен выглядеть как полноценный рейтинг.

## Графики и bar indicators

Текущие bars выглядят слишком примитивно и местами вводят в заблуждение.

Исправить правила отображения:

### Для процентов

- Значения 0–100 нормализовать к 100.
- Подписывать значение с `%`.
- Пример: `90%`.

### Для counts

- Не нормализовать каждое значение к самому себе.
- Нормализовать count bars относительно максимума в наборе.
- Если все значения равны 1, бары не должны выглядеть как “все максимальные и важные”.
- Добавить подпись:
  - “1 изменение”;
  - “6 включений”;
  - “1 выключение”.
- Если данных меньше 2 точек или все значения одинаковые, показывать fallback:
  - “Недостаточно данных для графика”.
  - Можно оставить компактный список без bar.

### Для top unstable targets

Если у всех targets одинаковый unstableScore:

- не показывать “топ” как рейтинг;
- показать блок “Изменения по целям”;
- или показать empty/insufficient state:
  - “Все цели менялись одинаково редко”.
  - “Недостаточно данных для рейтинга нестабильности”.

### Для availability top

- Значение показывать как `100%`, не `100`.
- Если все targets имеют 100%, показать:
  - “Все выбранные цели были доступны в выбранном периоде”.
- Не делать огромный список, если он не несёт разницы.

## Formatting rules

Добавить или использовать существующий formatter слой.

Нужны единые функции/методы по смыслу:

- formatPercent(value).
- formatCount(value).
- formatDurationMs(value).
- formatRelativeTime(value).
- formatDate(value).
- formatTargetLabel(value).
- formatEndpointLabel(value).
- formatCheckStatus(value).
- formatWhitelistDetectionResult(value).

Названия адаптировать под проект.

Требования:

1. Percent:
   - `0%`;
   - `40.2%`;
   - `85.7%`;
   - `100%`;
   - не показывать `NaN%`;
   - не показывать `Infinity%`;
   - clamp 0–100 только в UI formatter, если domain может временно дать плохое значение.
2. Duration:
   - `3861 мс`;
   - если >= 1000 мс, можно показывать `3.9 с`, если такой стиль уже используется.
3. Date/time:
   - “только что”;
   - “5 мин назад”;
   - абсолютная дата при старых значениях.
4. Unknown:
