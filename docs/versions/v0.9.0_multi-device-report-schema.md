## Новая версия

`v0.9.0 — Multi-Device Report Schema`

## Контекст

Локальная история, статистика, UI статистики и диагностика уже подготовлены в v0.8.x. Теперь нужно зафиксировать безопасный формат отчёта для будущего сбора данных с нескольких устройств.

## Проблема

Без стабильной схемы нельзя безопасно строить Worker: разные устройства будут присылать несовместимые данные, а в отчёт могут случайно попасть чувствительные поля.

## Цель версии

1. Добавить версионированные модели отчёта.
2. Собирать локальный `ReportBatch` из history/statistics.
3. Сериализовать отчёт в JSON.
4. Валидировать отчёт до будущей отправки.
5. Удалять чувствительные данные через sanitizer.
6. Не отправлять данные наружу в этой версии.

## Архитектурный принцип

Отчёт — отдельная contract/network model. Не использовать database entity или UI model как API contract. Схема: `CheckRun/Statistics -> ReportBuilder -> ReportSanitizer -> ReportValidator -> ReportBatch JSON`.

## Требования к реализации

- `ReportBatch`: `schemaVersion`, `appVersion`, `generatedAt`, `anonymousInstallationId`, `deviceReport`, `checkRuns`, `targetResults`, `statisticsSnapshot`, `privacyLevel`.
- `DeviceReport`: только безопасные поля — app/platform/version/network/operator/regionHint. Запрещены IMEI, IMSI, номер телефона, точные координаты, advertising id, токены.
- `CheckRunReport`: время начала/завершения, duration, triggerType, networkType, routeMode, overallStatus, success/failure/skipped counts.
- `CheckTargetResultReport`: checkRunId, targetId, safeLabel, safeHost без секретных query-параметров, routeKind, status, latencyMs, errorCode/errorCategory.
- `ReportSanitizer` должен удалять query-параметры, токены, headers, координаты, IMEI/IMSI/номер телефона и слишком длинные строки.
- `ReportValidator` должен проверять schemaVersion, batch size, timestamps, статусы, связи targetResults с checkRuns и отсутствие sensitive fields.

## Приватность и безопасность

Запрещено сохранять, показывать, отправлять или логировать:

- номер телефона;
- IMEI;
- IMSI;
- точные координаты;
- токены;
- bot token;
- shared secret;
- authorization headers;
- приватные URL и query-параметры с секретами;
- raw reports там, где пользователь должен видеть только агрегаты.

Если поле сомнительное — не включай его в публичный/серверный контракт без явного обоснования.

## Тесты

Добавь или обнови тесты, если инфраструктура проекта позволяет:

1. ReportBatch строится из истории проверок.
2. Пустая история даёт controlled-empty report.
3. Target results ссылаются на существующие checkRunId.
4. Sanitizer удаляет query-параметры и token-like поля.
5. Validator отклоняет отчёт без schemaVersion.
6. Validator отклоняет отрицательный latencyMs.
7. Validator отклоняет timestamps в будущем.
8. JSON сериализация/десериализация работает.
9. Схема не содержит IMEI/IMSI/номер телефона/точные координаты.
10. Слишком большой batch ограничивается.

Если тесты добавить невозможно без большого рефакторинга:

1. Не тащи новый тяжёлый тестовый стек.
2. Честно укажи это в отчёте.
3. Добавь подробный ручной сценарий проверки.
4. Сохрани код так, чтобы его можно было протестировать позже.

## Критерии готовности v0.9.0

Версия считается готовой только если:

1. Есть версионированная report schema.
2. ReportBatch строится из локальных данных.
3. ReportBatch сериализуется в JSON.
4. Validator и Sanitizer работают.
5. Sensitive fields не попадают в отчёт.
6. Отправки наружу нет.
7. Worker нет.
8. Telegram Bot нет.
9. Проект собирается.
10. CHANGELOG обновлён.
