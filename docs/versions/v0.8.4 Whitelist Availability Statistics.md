## Контекст

В v0.8.0 была добавлена история проверок:

- CheckRun.
- CheckTargetResult.
- локальное сохранение завершённых проверок.
- cleanup старых записей.

В v0.8.1 был добавлен Local Statistics Writer:

- общая статистика проверок.
- статистика по endpoint/target.
- статистика по routeKind.
- статистика по networkType/operator.
- daily statistics.
- rebuild статистики из истории.

В v0.8.2 был добавлен Statistics UI.

В v0.8.3 была укреплена надёжность статистики:

- diagnostics.
- consistency checker.
- rebuild.
- cleanup.
- защита UI от null/NaN/Infinity.
- обработка storage/statistics errors.

Теперь нужно исправить смысл статистики.

Проблема: текущая статистика в основном описывает проверки как технические запуски. Но пользователю важнее не только “сколько было проверок”, а “когда белые списки появлялись, исчезали, как часто были доступны и какие target/source чаще включались”.

Нужно доделать статистику проверок как базовый технический слой и добавить пользовательскую статистику появления белых списков:

- включение whitelist;
- выключение whitelist;
- длительность доступного состояния;
- частота появления;
- частота исчезновения;
- доступность по дням;
- доступность по target/source;
- простые графики/диаграммы на экране статистики.

## Главная цель версии

Добавить локальную статистику доступности белых списков поверх существующей истории проверок, не ломая текущую статистику проверок.

После реализации приложение должно показывать не только технические итоги проверок, но и историю изменения состояния whitelist: когда цель стала доступной, когда пропала, сколько времени была доступна и как часто появлялась.

## Важное разделение понятий

Разделить две разные сущности:

### Check statistics

Это статистика технических запусков проверки.

Примеры:

- всего проверок;
- успешных проверок;
- ошибочных проверок;
- частичных ошибок;
- среднее время проверки;
- последняя проверка;
- ошибки endpoint'ов;
- routeKind;
- networkType;
- operator.

### Whitelist availability statistics

Это статистика фактического состояния белых списков.

Примеры:

- whitelist был доступен;
- whitelist был недоступен;
- whitelist появился;
- whitelist исчез;
- сколько раз whitelist включался;
- сколько раз whitelist выключался;
- сколько времени whitelist был доступен;
- процент доступности;
- частота появления по дням;
- частота исчезновения по дням;
- топ стабильных targets;
- топ нестабильных targets.

Не смешивать эти две статистики в одной модели.

## Логика обнаружения включения/выключения

Нужно сравнивать состояние target между соседними проверками.

Минимальная логика:

1. Взять текущий CheckTargetResult.
2. Найти предыдущее сохранённое состояние этого же target/source.
3. Преобразовать результат проверки в WhitelistAvailabilityState.
4. Сравнить previousState и newState.
5. Если состояние изменилось:
   - UNAVAILABLE → AVAILABLE = BECAME_AVAILABLE.
   - AVAILABLE → UNAVAILABLE = BECAME_UNAVAILABLE.
   - UNKNOWN → AVAILABLE = UNKNOWN_TO_AVAILABLE.
   - UNKNOWN → UNAVAILABLE = UNKNOWN_TO_UNAVAILABLE.
6. Если состояние не изменилось:
   - AVAILABLE → AVAILABLE = STAYED_AVAILABLE.
   - UNAVAILABLE → UNAVAILABLE = STAYED_UNAVAILABLE.
7. Ошибки endpoint'а не должны автоматически считаться выключением whitelist, если в проекте можно отличить “target реально недоступен” от “проверка не смогла выполниться”.
8. Если различить нельзя, использовать UNKNOWN/ERROR, а не портить статистику ложным выключением.

Критически важно: ошибка проверки и исчезновение whitelist — не одно и то же.

## Обработка ошибок проверки

Не считать whitelist выключенным, если:

- нет сети;
- DNS error;
- timeout;
- storage error;
- check run cancelled;
- route/proxy failure;
- приложение не смогло выполнить проверку.

В таких случаях target должен получить UNKNOWN или ERROR_STATE, если нет достоверного результата.

Whitelist считается выключенным только если проверка достоверно показала, что target/source недоступен по правилам проекта.

## Rebuild whitelist statistics

Добавить rebuild новой статистики из существующей истории.

Минимальный алгоритм:

1. Прочитать CheckRun/CheckTargetResult в хронологическом порядке.
2. Для каждого target/source восстановить предыдущий state.
3. Сформировать WhitelistAvailabilityEvent.
4. Пересчитать summary.
5. Пересчитать daily availability.
6. Пересчитать target availability stats.
7. Сохранить агрегаты.
8. Не удалять историю проверок.
9. Очищать только агрегаты и события whitelist availability, если rebuild запускается для них.
10. Не запускать rebuild на каждом открытии экрана.
11. Rebuild должен быть явным или запускаться только при необходимости schema/version migration.

Если существующий rebuild statistics уже есть, не ломай его. Добавь отдельный rebuild для whitelist availability или расширь существующий аккуратно, если архитектура проекта уже предполагает общий rebuilder.

## Cleanup

Добавить cleanup для whitelist availability data.

Требования:

1. Cleanup не должен удалять последнюю известную запись состояния target.
2. Cleanup не должен оставлять агрегаты без исходных событий, если они больше не согласованы.
3. Cleanup daily availability должен быть согласован с retention policy.
4. Cleanup all-time summary не должен удаляться вместе с daily data.
5. Значения retention должны быть именованными константами.
6. Не оставлять магические числа внутри методов.
7. После cleanup экран статистики не должен падать.
8. После cleanup rebuild должен восстанавливать корректное состояние из оставшейся истории.

# v0.8.4 — Whitelist Availability Statistics

## Цель

Добавить локальную статистику появления и исчезновения белых списков поверх существующей истории проверок.

## Входит в версию

- Модель события изменения состояния whitelist.
- Сохранение событий включения/выключения whitelist.
- Расчёт summary доступности whitelist.
- Daily availability statistics.
- Target availability statistics.
- Rebuild whitelist availability statistics из истории проверок.
- Cleanup whitelist availability events/statistics.
- UI-блок “Статистика белых списков”.
- Простые графики доступности, включений/выключений и нестабильных targets.
- Empty/loading/error/stale states.
- Защита UI от null/NaN/Infinity.
- Тесты или ручной checklist.

## Не входит в версию

- Worker.
- Telegram Bot.
- Multi-device reports.
- Отправка данных наружу.
- Публичные отчёты.
- Синхронизация между устройствами.
- Экспорт CSV/JSON.
- Сложные фильтры.
- Прогнозирование.
- Репутация источников.
- Карты.
- Полная переработка Statistics UI.
- Изменение check/proxy/routing logic без необходимости.

## Архитектурные ограничения

- Статистика проверок и статистика whitelist availability должны быть разделены.
- Ошибка проверки не должна автоматически считаться выключением whitelist.
- UI не должен считать статистику сам.
- Domain/data/UI не смешивать.
- Пользовательские строки вынести в ресурсы.
- Не показывать и не логировать чувствительные данные.
- Не добавлять функции будущих версий.

## Ручное тестирование

Проверить вручную на устройстве или эмуляторе:

1. Обновиться с v0.8.3.
   Ожидается: приложение запускается, главный экран работает, старая статистика проверок не потеряна.

2. Выполнить первую проверку.
   Ожидается: появляется базовое состояние targets, но ложные включения/выключения не создаются без предыдущего состояния.

3. Выполнить вторую проверку без изменения состояния.
   Ожидается: нет ложных событий включения/выключения.

4. Смоделировать появление whitelist.
   Ожидается: создаётся событие BECAME_AVAILABLE.

5. Смоделировать исчезновение whitelist.
   Ожидается: создаётся событие BECAME_UNAVAILABLE.

6. Отключить сеть и выполнить проверку.
   Ожидается: ошибка проверки сохраняется, но whitelist не считается выключенным автоматически.

7. Использовать endpoint с timeout/DNS error.
   Ожидается: target получает UNKNOWN/ERROR, но не ложное BECAME_UNAVAILABLE.

8. Открыть экран статистики.
   Ожидается: виден блок “Статистика белых списков”.

9. Проверить график доступности по дням.
   Ожидается: график отображается, пустые данные не ломают UI.

10. Проверить график включений/выключений.
    Ожидается: включения и выключения отображаются раздельно.

11. Проверить топ нестабильных targets.
    Ожидается: список ограничен top N и не ломает layout.

12. Проверить топ targets по доступности.
    Ожидается: проценты корректные, нет NaN/Infinity.

13. Перезапустить приложение.
    Ожидается: статистика whitelist не пропала.

14. Запустить rebuild, если есть diagnostics-кнопка.
    Ожидается: whitelist availability statistics пересчиталась из истории.

15. Проверить cleanup.
    Ожидается: свежие данные и последнее состояние target не потеряны.

16. Проверить светлую и тёмную тему.
    Ожидается: графики и статистика читаются нормально.

17. Проверить маленький экран.
    Ожидается: графики не ломают layout.

18. Проверить логи.
    Ожидается: нет токенов, секретов, IMSI, IMEI, номера телефона, точных координат и приватных URL.

19. Проверить главный экран.
    Ожидается: last check state из v0.7.2 не сломан.

20. Проверить старую статистику проверок.
    Ожидается: check statistics и whitelist availability statistics отображаются раздельно.
