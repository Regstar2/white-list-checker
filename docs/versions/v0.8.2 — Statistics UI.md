## Текущая версия

v0.8.1

## Новая версия

v0.8.2 — Statistics UI

## Контекст

В v0.8.0 был добавлен фундамент сохранения истории проверок.

В v0.8.1 был добавлен Local Statistics Writer:

- общая статистика проверок;
- статистика по endpoint/target;
- статистика по routeKind;
- статистика по networkType/operator;
- статистика по дням;
- rebuild статистики из истории.

Теперь нужно добавить UI для просмотра этой статистики.

Важно: v0.8.2 — это только отображение уже существующей локальной статистики. Не нужно заново считать статистику в UI и не нужно добавлять Worker, Telegram Bot, multi-device reports или отправку данных наружу.

## Проблема

Статистика уже записывается локально, но пользователь её не видит.

Нужно добавить понятный экран статистики и короткую сводку на главном экране, не превращая главный экран в перегруженную аналитическую панель.

Добавить UI для локальной статистики.

1. Короткую сводку статистики на главном экране.

4. Статистику по endpoints/targets.

## Основной принцип реализации

UI должен отображать статистику, а не рассчитывать её заново.

Предпочтительная схема:

StatisticsRepository
→ StatisticsViewModel / StatisticsStateHolder
→ StatisticsUiState
→ StatisticsScreen

Для главного экрана:

StatisticsRepository
→ HomeViewModel / HomeStateHolder
→ HomeStatisticsSummaryUiState
→ компактная карточка на главном экране

Если в проекте используется другая архитектура, следуй ей, но не смешивай UI, domain и data.

## UI state

Добавь явную модель состояния UI.

Предпочтительный смысл:

StatisticsUiState:
- Loading
- Empty
- Content
- Error

Content должен содержать:

- summary.
- targetStatistics.
- routeKindStatistics.
- networkStatistics.
- dailyStatistics.
- lastUpdatedAt.
- isStale.

HomeStatisticsSummaryUiState:
- Hidden или Empty.
- Loading, если главный экран уже поддерживает loading-состояния.
- Content.
- Error, только если для главного экрана это действительно полезно.

Не показывай пользователю сырые entity/database-модели.

Если в проекте уже есть UiState-паттерн — используй существующий стиль.

## Главный экран

На главном экране нужна только короткая сводка, без перегруза.

Добавить компактную карточку или секцию по смыслу:

- всего проверок;
- процент успеха;
- последняя успешная проверка;
- серия ошибок подряд, если больше 0;
- кнопка или ссылка “Статистика”.

Главный экран не должен превращаться в полный экран аналитики.

Не ломать блок последней проверки из v0.7.2.

Важно:

- stale-состояние последней проверки должно продолжать работать;
- последняя проверка не должна скрываться;
- статистическая сводка не должна конфликтовать с last check state.

## Экран “Статистика”

Добавить отдельный экран “Статистика”.

Минимальные секции:

1. Общая статистика.
2. Последние показатели.
3. Endpoints / Targets.
4. Route kinds.
5. Сеть / оператор.
6. По дням.

### 1. Общая статистика

Показать:

- всего проверок;
- успешных проверок;
- частично успешных проверок, если есть;
- ошибочных проверок;
- процент успеха;
- среднюю задержку;
- последнюю проверку;
- последнюю успешную проверку;
- последнюю ошибочную проверку;
- серию ошибок подряд.

### 2. Последние показатели

Показать кратко:

- данные обновлены: X минут назад / X часов назад / X дней назад;
- данные устарели, если последняя проверка старая;
- если статистики мало, показать предупреждение, что выводы могут быть неточными.

### 3. Endpoints / Targets

Показать список endpoints/targets.

Для каждого элемента:

- название или host;
- всего проверок;
- процент успеха;
- средняя задержка;
- последняя проверка;
- последний статус.

Сортировка по умолчанию:

- проблемные выше;
- затем часто проверяемые;
- либо использовать существующую сортировку, если она уже есть в проекте.

Не делать сложные фильтры в этой версии.

### 4. Route kinds

Показать статистику по routeKind:

- routeKind;
- всего проверок;
- успешность;
- средняя задержка;
- последняя проверка.

### 5. Сеть / оператор

Показать статистику по networkType/operator:

- networkType;
- operator;
- всего проверок;
- успешность;
- средняя задержка;
- последняя проверка.

Если operator недоступен, показывать аккуратное fallback-состояние, а не null.

### 6. По дням

Показать простую дневную статистику списком.

Без сложных графиков.

Минимально:

- дата;
- всего проверок;
- успешные;
- ошибочные;
- процент успеха;
- средняя задержка.

Если позже нужны графики — это отдельная версия, не v0.8.2.

## Empty state

Если статистики ещё нет, показать понятное состояние:

- статистика ещё не собрана;
- выполните проверку, чтобы появились данные.

Не показывать пустые списки без объяснения.

## Loading state

Если статистика загружается, показать loading-состояние в стиле проекта.

Не блокировать весь главный экран, если грузится только статистическая сводка.

## Error state

Если статистику не удалось загрузить:

1. Показать понятное сообщение.
2. Не ломать главный экран целиком.
3. Дать возможность повторить загрузку, если в архитектуре уже есть retry.
4. Логировать техническую ошибку без секретов.
5. Не проглатывать ошибку молча.

## Stale state

Если последняя проверка была давно, UI статистики должен показывать, что данные устарели.

Важно:

- stale != empty;
- старая статистика должна отображаться;
- пользователь должен понимать, что данные есть, но они давно не обновлялись.

Использовать существующий механизм stale из v0.7.2, если он подходит.

Не дублировать логику свежести в нескольких местах.

## Форматирование значений

Не форматировать значения хаотично прямо в UI.

Требования:

1. Проценты показывать аккуратно, например 85% или 85.4%, в зависимости от стиля проекта.
2. Latency показывать в ms.
3. Время показывать как относительное, если в проекте уже есть такой формат: “5 минут назад”, “2 часа назад”.
4. Не показывать null пользователю.
5. Если значения нет, использовать понятный fallback: “нет данных”, “неизвестно”, “недостаточно данных”.
6. Все пользовательские строки — в ресурсы.

Если в проекте уже есть formatter для времени, статусов или процентов — использовать его.

Если formatter отсутствует, добавить минимальный StatisticsValueFormatter или использовать существующий форматирующий слой проекта.

Не создавать общий Utils.

Примеры строк по смыслу:

- Статистика.
- Общая статистика.
- Endpoints.
- Маршруты.
- Сеть и оператор.
- По дням.
- Всего проверок.
- Успешность.
- Средняя задержка.
- Последняя проверка.
- Последняя успешная.
- Последняя ошибка.
- Серия ошибок.
- Данные устарели.
- Статистика ещё не собрана.
- Выполните проверку, чтобы появились данные.
- Не удалось загрузить статистику.
- Повторить.

Не хардкодить пользовательские строки в Kotlin/Java-коде.

## Навигация

Добавить переход на экран статистики в существующем стиле приложения.

Допустимые варианты:

- кнопка/карточка на главном экране;
- пункт в нижней навигации, если там уже есть место и стиль;
- пункт в drawer/settings, если так устроено приложение.

Не переделывать всю навигацию ради одного экрана.

Если приложение уже перегружено экранами, предпочтительно сделать переход с главного экрана через компактную карточку.

## Material/UI стиль

Следуй текущему стилю приложения.

Если проект использует Material 3:

- использовать существующие Card / ListItem / Text / Button компоненты;
- соблюдать отступы;
- не делать мелкие touch targets;
- поддерживать светлую и тёмную тему;
- не добавлять случайные цвета вне темы;
- не делать UI плотной таблицей, если это плохо читается на телефоне.

Если проект использует XML layout, следуй существующему XML-стилю.

Если проект использует Jetpack Compose, следуй существующему Compose-стилю.

## Производительность

Не загружать и не пересчитывать всю историю проверок прямо на UI.

UI должен читать готовые агрегаты из StatisticsRepository.

Если списки могут быть длинными:

- ограничить количество отображаемых endpoints/targets;
- например показывать top 10 / top 20;
- не рендерить тысячи элементов без необходимости;
- использовать lazy list, если проект на Compose.

Не делать тяжёлые операции на main thread.

## Приватность и безопасность

Не показывать лишние чувствительные данные.

Запрещено отображать:

- номер телефона;
- IMSI;
- IMEI;
- точные координаты;
- токены;
- секреты;
- приватные URL, если они не должны быть видны пользователю;
- содержимое заголовков авторизации;
- любые данные, которые могут раскрыть личность пользователя без необходимости.

Если endpoint/target содержит чувствительные данные, показывать безопасный label или host без секретных query-параметров.

В v0.8.2 не добавлять отправку данных наружу.

## Ручное тестирование

Проверить вручную на устройстве или эмуляторе:

1. Обновиться с v0.8.1.
   Ожидается: приложение запускается, главный экран работает.

2. Открыть главный экран без статистики.
   Ожидается: нет падения, есть понятное empty-состояние или статистическая карточка скрыта корректно.

3. Выполнить успешную проверку.
   Ожидается: статистическая сводка на главном экране обновляется.

4. Выполнить ошибочную проверку.
   Ожидается: статистика ошибок обновляется, главный экран не ломается.

5. Открыть экран “Статистика”.
   Ожидается: отображается общая статистика.

6. Проверить endpoints/targets.
   Ожидается: список показывает счётчики, успешность, задержку и последнюю проверку.

7. Проверить routeKind.
   Ожидается: routeKind отображаются отдельно и не смешиваются.

8. Проверить network/operator.
   Ожидается: network/operator-статистика отображается корректно, null не показывается пользователю.

9. Проверить daily statistics.
   Ожидается: дневная статистика отображается простым списком.

10. Проверить stale state.
   Ожидается: если последняя проверка старая, статистика отображается, но помечается как устаревшая.

11. Проверить перезапуск приложения.
   Ожидается: статистика сохраняется и отображается после перезапуска.

12. Проверить светлую и тёмную тему.
   Ожидается: экран читается в обеих темах.

13. Проверить маленький экран.
   Ожидается: элементы не обрезаются критично, списки скроллятся.

14. Проверить логи.
   Ожидается: в логах нет токенов, секретов, IMSI, IMEI, номера телефона и лишних приватных данных.

## Ограничения diff

Не принимать большой расползающийся diff.

Если для добавления Statistics UI понадобилось изменить много файлов, сначала остановись и проверь:

1. Не началась ли новая запись статистики.
2. Не переписывается ли Local Statistics Writer из v0.8.1.
3. Не переписывается ли persistence foundation из v0.8.0.
4. Не появился ли Worker.
5. Не появился ли Telegram Bot.
6. Не появилась ли отправка данных наружу.
7. Не добавились ли сложные графики.
8. Не добавился ли экспорт.
9. Не переписывается ли check algorithm.
10. Не переписывается ли главный экран целиком.
11. Не меняется ли routing/proxy logic без необходимости.
12. Не добавляются ли зависимости без явной пользы.
13. Не появились ли классы с неясной ответственностью.
14. Не нарушено ли разделение UI/domain/data.

Если diff стал слишком большим, уменьши scope и сделай только базовый экран статистики и компактную сводку на главном экране.

## Критерии готовности v0.8.2

Версия считается готовой только если:

- главный экран показывает компактную статистическую сводку;
- блок последней проверки из v0.7.2 не сломан;
- есть отдельный экран “Статистика”;
- экран статистики использует готовые агрегаты из v0.8.1;
- UI не пересчитывает статистику из всей истории вручную;
- отображается общая статистика;
- отображается статистика по endpoint/target;
- отображается статистика по routeKind;
- отображается статистика по networkType/operator;
- отображается daily statistics;
- есть loading state;
- есть empty state;
- есть error state;

- пользователь не видит null;
- пользовательские строки вынесены в ресурсы;
- чувствительные данные не отображаются;
- главный экран не перегружен;
- нет сложных графиков;
- нет экспорта;
- нет Worker;
- нет Telegram Bot;
- нет отправки данных наружу;
- domain/data/UI не смешаны без необходимости;
- логика покрыта тестом или описан ручной тест;
- проект собирается;
- CHANGELOG обновлён;
