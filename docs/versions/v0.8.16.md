# v0.8.16 - migrate existing relay Worker to public service

## Scope

v0.8.16 converts the existing Cloudflare Worker instance:

```text
whitelist-monitor-tg-relay
```

into the central WhiteListChecker public service:

```text
https://whitelist-monitor-tg-relay.carkov195.workers.dev
```

The Worker name is historical. It was previously used by the project owner as a personal Telegram relay, but this same instance is now used as the shared central service for Android API, public Telegram bot, anonymized reports, linked devices, remote commands and public status aggregation.

No new Worker named `whitelistchecker-public-service` is created.

## Two Independent Telegram Scenarios

General service:

```text
Android
-> BuildConfig.PUBLIC_SERVICE_BASE_URL
-> whitelist-monitor-tg-relay
-> D1
-> shared Telegram bot
```

Personal Telegram relay:

```text
Android
-> user Worker URL
-> user Relay Secret
-> user Telegram bot
```

The Android settings for a personal Worker URL, Relay Secret and recipients remain separate from the built-in public service URL.

## Changed

- `cloudflare/public-service/wrangler.toml` now targets `name = "whitelist-monitor-tg-relay"`.
- Android debug and release builds now use `https://whitelist-monitor-tg-relay.carkov195.workers.dev` as `BuildConfig.PUBLIC_SERVICE_BASE_URL`.
- The public Telegram bot inline keyboard is production-ready:
  - main menu;
  - status refresh;
  - region/operator selection with main-menu return;
  - linked device list and device screen;
  - two-step unlink confirmation.
- User-facing new Telegram texts are centralized in `publicBotFormatter.ts`.
- Device aliases and other external values are escaped before insertion into Telegram HTML.
- Worker package metadata now uses the historical Worker name.
- Documentation now explains that the project owner's old personal relay instance becomes the central service.

## Preserved

- Personal relay template: `docs/cloudflare-worker/telegram-relay-worker.js`.
- Android personal relay settings and storage.
- Android `/tg/getMe`, `/tg/getUpdates` and `/tg/sendMessage` client flow for user-owned relay Workers.
- User-owned Telegram bot setup docs.
- D1 schema and migrations.

The old owner-owned `/tg/*` instance may stop working at `whitelist-monitor-tg-relay` after the central service deployment. Other users can still create their own personal relay Worker from the template.

## Runtime Secrets

The central service expects:

```text
PUBLIC_BOT_TOKEN
TELEGRAM_WEBHOOK_SECRET
DEVICE_TOKEN_PEPPER
ADMIN_API_SECRET
```

Migration notes:

- `PUBLIC_BOT_TOKEN` may receive the previous `BOT_TOKEN` value if the old personal bot becomes the shared public bot.
- `TELEGRAM_WEBHOOK_SECRET` must be a new random string.
- `DEVICE_TOKEN_PEPPER` must be a separate random string.
- `ADMIN_API_SECRET` must be a third separate random string.
- Old `BOT_TOKEN` and `RELAY_SECRET` can be removed only after the transition is verified.

Never place secrets in the repository.

## Telegram Webhook

Webhook URL:

```text
https://whitelist-monitor-tg-relay.carkov195.workers.dev/telegram/webhook
```

Manual setup after deploy:

1. Deploy the Worker.
2. Add runtime secrets.
3. Set Telegram webhook to `/telegram/webhook`.
4. Pass `secret_token` equal to `TELEGRAM_WEBHOOK_SECRET`.
5. Set `allowed_updates` to `message` and `callback_query`.
6. Check `getWebhookInfo`.
7. Send `/start` to the bot.

Setting a webhook disables `getUpdates` for the same Telegram bot. This is expected when the previous bot becomes the shared public bot.

## Manual Telegram Check

1. Send `/start`.
2. Verify the main menu buttons.
3. Open status and use `Обновить`.
4. Open region and operator lists and return with `Главное меню`.
5. Open `Мои устройства`.
6. Open a linked device.
7. Use `Проверить сейчас` only for a linked device with remote checks enabled.
8. Tap `Отвязать устройство` and verify D1 is unchanged before confirmation.
9. Tap `Отмена`.
10. Repeat unlink and confirm with `Да, отвязать`.
