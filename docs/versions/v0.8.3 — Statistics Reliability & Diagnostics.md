## Контекст

В v0.7.2 была исправлена логика отображения последней проверки.

В v0.8.0 была добавлена история проверок:

- CheckRun.
- CheckTargetResult.
- локальное сохранение завершённых проверок;
- cleanup старых записей.

В v0.8.1 был добавлен Local Statistics Writer:

- общая статистика;
- статистика по endpoint/target;
- статистика по routeKind;
- статистика по networkType/operator;
- daily statistics;
- rebuild статистики из истории.

В v0.8.2 был добавлен Statistics UI:

- краткая статистика на главном экране;
- отдельный экран “Статистика”;
- loading/empty/error/stale-состояния.

Теперь нужно стабилизировать статистику и добавить диагностику, чтобы проверить, что история и статистика не ломаются при перезапуске, обновлении, ошибках storage, ошибках endpoint'ов, cleanup и rebuild.

Важно: v0.8.3 — это reliability и diagnostics. Это не новая аналитика и не публичная функция.

## Проблема

История и статистика уже реализованы, но нужно убедиться, что они устойчивы в реальных условиях:

1. После перезапуска приложения.
2. После обновления версии.
3. При ошибках endpoint'ов.
4. При отсутствии сети.
5. При повреждённом или частично недоступном storage.
6. После cleanup старых записей.
7. После rebuild статистики.
8. При большом количестве сохранённых проверок.
9. При несовпадении истории и агрегированной статистики.

Без этой версии следующая стадия с multi-device reports и Worker будет строиться на ненадёжном локальном фундаменте.

## Цель версии

Укрепить локальную историю и статистику.

После реализации приложение должно:

1. Проверять согласованность CheckRun, CheckTargetResult и агрегированной статистики.
2. Иметь диагностический блок для истории и статистики.
3. Уметь безопасно rebuild-ить статистику из истории.
4. Корректно обрабатывать ошибки чтения/записи статистики.
5. Корректно работать после перезапуска приложения.
6. Корректно работать после обновления с v0.8.2.
7. Корректно очищать старые записи.
8. Не терять последнюю проверку.
9. Не показывать пользователю мусорные null/NaN/Infinity значения.
10. Не ломать главный экран и экран статистики.

## Основной принцип реализации

v0.8.3 должна укрепить уже существующую систему, а не заменить её.

Предпочтительная схема:

CheckHistoryRepository
→ StatisticsRepository
→ StatisticsDiagnosticsReader
→ StatisticsDiagnosticsUiState или внутренний debug/diagnostics state
→ Diagnostics UI или существующий diagnostics/debug блок

Consistency check:

CheckHistoryRepository.getRecentCheckRuns(...)
+ CheckHistoryRepository.getTargetResults(...)
+ StatisticsRepository.getSummary(...)
→ StatisticsConsistencyChecker
→ StatisticsConsistencyReport

Rebuild:

CheckHistoryRepository.getAllForStatisticsRebuild(...)
→ LocalStatisticsRebuilder.rebuildFromHistory(...)
→ StatisticsRepository.replaceAll(...)
→ StatisticsDiagnosticsReader.getDiagnostics()

Названия можно адаптировать под существующий стиль проекта.

Не использовать названия без точной ответственности:

- DiagnosticsManager.
- StatisticsManager.
- StatsHelper.
- StatsUtils.
- DataProcessor.
- StorageHandler.

## Проверка согласованности

Добавь проверку согласованности между историей и статистикой.

Минимальные проверки:

1. Если checkRunCount > 0, summary должен существовать.
2. totalRuns в summary не должен быть больше checkRunCount, если логика не допускает такого.
3. successRuns + partialFailureRuns + failureRuns + cancelledRuns + unknownRuns не должны превышать totalRuns.
4. target statistics не должны существовать без target results, если история не была очищена отдельно.
5. daily statistics должны соответствовать диапазону дат истории, если daily cleanup не удалил старые дни.
6. lastRunAt не должен быть позже текущего времени.
7. lastStatisticsUpdatedAt не должен быть раньше последнего сохранённого check run, если после него должен был быть update.
8. successRate не должен быть NaN, Infinity или отрицательным.
9. averageLatencyMs не должен быть NaN, Infinity или отрицательным.
10. consecutiveFailureCount не должен быть отрицательным.

Consistency warning — это диагностическое предупреждение, а не причина падения приложения.

## Rebuild статистики

Проверь существующий rebuild из v0.8.1.

Если он есть, укрепи его:

1. Rebuild должен работать из сохранённой истории.
2. Rebuild не должен удалять историю проверок.
3. Rebuild должен очищать только агрегаты статистики.
4. Rebuild должен быть атомарным настолько, насколько позволяет текущий storage.
5. Если rebuild упал, приложение не должно остаться в полностью сломанном состоянии.
6. После rebuild diagnostics должны показывать актуальные значения.
7. Rebuild не должен выполняться автоматически на каждом запуске без причины.
8. Rebuild может быть доступен через внутренний diagnostics/debug блок, если такой блок уже есть.

Если rebuild ещё нет или он был заглушкой, добавь минимальную безопасную реализацию.

## Cleanup

Проверь cleanup из v0.8.0 и v0.8.1.

Требования:

1. Cleanup истории не должен удалять последнюю проверку, если это единственная доступная запись.
2. Cleanup target results не должен оставлять висячие target results без CheckRun.
3. Cleanup CheckRun не должен оставлять orphan target results.
4. Cleanup daily statistics должен быть согласован с retention policy.
5. Cleanup all-time summary не должен удаляться вместе с daily statistics.
6. После cleanup consistency checker не должен выдавать критические ошибки.
7. Значения retention должны быть именованными константами.
8. Не оставлять магические числа внутри методов.

Если используется Room/SQLite, cleanup должен быть безопасным по foreign keys или явной последовательности удаления.

Если используется file-based storage, cleanup должен защищаться от повреждения файла.

- null;
- NaN;
- Infinity;
- -1 ms;
- отрицательный процент;

- неизвестно;

## Ручное тестирование

Проверить вручную на устройстве или эмуляторе:

1. Обновиться с v0.8.2.
   Ожидается: приложение запускается, главный экран работает, статистика отображается.

2. Выполнить успешную проверку.
   Ожидается: история, статистика и diagnostics обновляются.

3. Выполнить ошибочную проверку.
   Ожидается: ошибка сохраняется, статистика ошибок обновляется, UI не падает.

4. Выполнить несколько проверок подряд.
   Ожидается: totalRuns и targetResultCount соответствуют ожиданиям.

5. Перезапустить приложение.
   Ожидается: история и статистика не пропадают.

6. Открыть экран статистики.
   Ожидается: нет null, NaN, Infinity и сломанных значений.

7. Открыть diagnostics-блок.
   Ожидается: отображаются counts, даты и consistency status.

8. Запустить rebuild статистики, если добавлена кнопка или внутренний сценарий.
   Ожидается: статистика пересчитывается из истории, история не удаляется.

9. Запустить cleanup, если есть внутренний способ.
   Ожидается: старые записи очищаются безопасно, orphan records не остаются.

10. Отключить сеть и выполнить проверку.
    Ожидается: ошибочный результат сохраняется, статистика обновляется, приложение не падает.

11. Проверить endpoint с timeout/DNS error.
    Ожидается: CheckTargetResult и статистика отображают ошибку корректно.

12. Проверить светлую и тёмную тему.
    Ожидается: diagnostics и Statistics UI читаются нормально.

13. Проверить маленький экран.
    Ожидается: diagnostics и Statistics UI не ломают layout.

14. Проверить логи.
    Ожидается: нет токенов, секретов, IMSI, IMEI, номера телефона, точных координат и приватных URL.

15. Проверить главный экран.
    Ожидается: last check state из v0.7.2 не сломан.
