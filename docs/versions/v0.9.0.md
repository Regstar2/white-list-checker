# v0.9.0 — Custom DNS and Android Private DNS independence

## Цель

WhiteListChecker должен выполнять полноценную проверку мобильной сети при включённом Android Private DNS, самостоятельно разрешая контрольные домены через управляемый пользователем набор DNS и используя доступность DNS как второй независимый диагностический сигнал.


## Реализовано

### DNS settings

Добавлена отдельная domain/data/UI-модель DNS:

- `EditableDnsServer`;
- `DnsServerProtocol`;
- `DnsCheckResult`;
- `DnsCheckErrorType`;
- `DnsWhitelistSignal`;
- `DefaultDnsServers`;
- `DnsServersRepository`;
- `DnsServersJsonCodec`.

DNS хранятся в отдельном DataStore `dns_servers` и не затрагивают пользовательский список сайтов.

Стандартный набор:

```text
FOREIGN
Cloudflare  1.1.1.1:53
Google      8.8.8.8:53

LOCAL
Yandex DNS            77.88.8.8:53
Yandex DNS Secondary  77.88.8.1:53
```

Built-in DNS имеют стабильные ID. Удалённые built-in ID сохраняются как tombstones, поэтому намеренно удалённая запись не возвращается после перезапуска, а будущий новый built-in может быть добавлен миграцией. Reset очищает tombstones и восстанавливает стандартный набор.

Нельзя отключить или удалить последний enabled DNS.

### UI

Экран «Настройки проверки» разделён на вкладки:

```text
[ Сайты ] [ DNS ]
```

DNS-вкладка содержит:

- «Внешние DNS»;
- «Локальные DNS»;
- checkbox enabled;
- имя;
- endpoint;
- протокол;
- удаление;
- добавление DNS;
- reset defaults.

Первая версия raw DNS принимает literal IPv4 endpoint, порт `1..65535` и протокол `DNS / UDP + TCP`.

### Cellular DNS transport

Добавлены:

- `DnsPacketCodec`;
- `CellularDnsTransport`;
- `DnsQueryClient`;
- `CellularDnsProbe`;
- `CellularDnsResolver`.

DNS-запросы:

- UDP socket связывается через `Network.bindSocket(DatagramSocket)`;
- TCP fallback создаётся через `Network.socketFactory`;
- системный DNS Android не используется для поиска самого resolver;
- поддерживаются A и AAAA ответы для target resolution;
- truncated UDP response повторяется через TCP;
- проверяется transaction ID и структура ответа;
- NXDOMAIN и SERVFAIL типизированы;
- cache hostname → addresses существует только на время одного check run.

### Target HTTPS checks

`MobileSiteChecker` использует один OkHttp client на check run:

```text
socketFactory = cellular Network.socketFactory
dns = CellularDnsResolver
```

URL остаётся hostname-based, поэтому штатные механизмы OkHttp сохраняют:

- TLS certificate validation;
- hostname verification;
- SNI;
- redirects.

Не добавлены trust-all сертификаты или отключение hostname verification.

### Один Network на run

`WhitelistCheckUseCase`:

1. загружает enabled sites;
2. загружает enabled DNS;
3. запрашивает cellular `Network`;
4. выполняет DNS probes через него;
5. выбирает все доступные resolvers независимо от FOREIGN/LOCAL группы;
6. создаёт run-local `CellularDnsResolver`;
7. проверяет сайты через OkHttp и тот же cellular `Network`;
8. строит site и DNS summaries;
9. классифицирует site + DNS signals;
10. сохраняет структурированные поля в `NetworkCheckResult`;
11. освобождает cellular callback в `finally`.

### Private DNS diagnostics

В `NetworkCheckResult` добавлены:

- `privateDnsActive`;
- `privateDnsServerName`;
- `customDnsUsed`.

Private DNS диагностируется, но не участвует в выборе DNS route.

### DNS signal

`DnsWhitelistSignalClassifier`:

```text
FOREIGN <= 25%, LOCAL >= 50% -> WHITELIST_LIKE
FOREIGN >= 50%, LOCAL >= 50% -> NORMAL
FOREIGN == 0, LOCAL == 0     -> NO_DNS_ACCESS
иначе                         -> PARTIAL
```

Сайты остаются первичным сигналом.

Конфликты:

```text
SITE WHITELIST_ON + DNS NORMAL          -> PARTIAL_PROBLEM
SITE WHITELIST_OFF + DNS WHITELIST_LIKE -> PARTIAL_PROBLEM
```

DNS-only блокировка не создаёт `WHITELIST_ON`.

### Diagnostics report

Подробный отчёт отображает:

- active / checked network;
- Private DNS active/inactive;
- Private DNS server name;
- custom DNS used/not used;
- FOREIGN/LOCAL DNS summary;
- каждый DNS endpoint;
- latency;
- typed error;
- Site signal;
- DNS signal;
- final state.

DNS diagnostics остаются локальными и не добавляются автоматически в public-service JSON contract.

## Ручной тест-план

### 1. Private DNS выключен

1. Mobile data ON.
2. Выполнить проверку.
3. Проверить FOREIGN/LOCAL DNS.
4. Проверить FOREIGN/LOCAL sites.
5. `Custom DNS` должен быть `used`, если есть доступный resolver.

### 2. Private DNS Automatic

Повторить тест 1. Результат не должен принципиально меняться только из-за системного режима DNS.

### 3. Private DNS strict

1. Включить реальный Private DNS hostname.
2. Выполнить проверку.
3. Убедиться, что Private DNS отображается как active.
4. Убедиться, что Custom DNS = used.
5. DNS probes и sites должны выполняться.

### 4. Wi-Fi ON + mobile data ON

Активная сеть может быть Wi-Fi, проверяемая должна быть Mobile. DNS и HTTPS target traffic должны оставаться на cellular Network.

### 5. Disable FOREIGN DNS

Отключённая запись не должна probe/resolver/classification.

### 6. Disable LOCAL DNS

Аналогично.

### 7. Add FOREIGN DNS

Добавить literal IPv4 resolver, перезапустить приложение, убедиться в сохранении.

### 8. Add LOCAL DNS

Аналогично.

### 9. Delete DNS

Удалить запись и перезапустить приложение. Она не должна появиться снова. Удалённый built-in возвращается только после Reset.

### 10. Reset DNS

Должен восстановиться стандартный набор FOREIGN/LOCAL DNS с enabled = true.

### 11. VPN

Проверить, что приложение не заявляет гарантированный VPN bypass. Поведение зависит от политики конкретного VPN.

## Ограничения

- Custom DNS endpoint v0.9.0 — literal IPv4; hostname endpoint намеренно запрещён, чтобы не создавать зависимость от системного DNS.
- DNS/53 transport не шифруется.
- Custom DNS не гарантирует обход произвольного VPN.
- Приложение не меняет Android Private DNS и не создаёт VPN/proxy.
- Figma MCP layout verification требует доступного лимита Figma integration; функциональный UI должен дополнительно сравниваться с макетом вручную.
