## Контекст

В версии v0.8.0 был добавлен фундамент локального сохранения результатов проверок:

- CheckRun.
- CheckTargetResult.
- Локальное сохранение завершённых проверок.
- Repository для истории проверок.
- Cleanup старых записей.

Теперь нужно добавить локальную запись и обновление статистики поверх сохранённой истории проверок.

Важно: v0.8.1 — это не экран статистики. Это только слой расчёта и сохранения локальных агрегированных метрик, которые будут использоваться в v0.8.2 Statistics UI.

## Проблема

После v0.8.0 приложение сохраняет историю проверок, но ещё не имеет готового слоя статистики.

Если в будущем считать статистику прямо на UI каждый раз из всей истории, это приведёт к:

- дублированию логики;
- тяжёлым запросам;
- размазыванию правил по ViewModel/UI;
- сложному тестированию;
- нестабильному поведению при большом количестве проверок.

Нужен отдельный Local Statistics Writer, который будет обновлять локальные агрегаты после завершения проверки или по явному rebuild-сценарию.

## Цель версии

Добавить локальный слой записи и обновления статистики.

После реализации приложение должно:

1. Использовать сохранённые CheckRun и CheckTargetResult из v0.8.0.
2. Обновлять локальные статистические агрегаты после завершения проверки.
3. Считать базовые метрики:
   - всего проверок;
   - успешных проверок;
   - ошибочных проверок;
   - частично успешных проверок;
   - процент успеха;
   - средняя задержка;
   - последняя успешная проверка;
   - последняя ошибочная проверка;
   - серия ошибок подряд.
4. Считать статистику по:
   - endpoint/target;
   - routeKind;
   - networkType;
   - operator;
   - дню.
5. Иметь возможность пересобрать статистику из истории проверок.
6. Не добавлять UI статистики.
7. Не отправлять данные наружу.
8. Не ломать главный экран и last check state.

## Основной принцип реализации

Статистика должна быть отдельной ответственностью.

Не делать один класс, который одновременно:

- выполняет проверку;
- сохраняет CheckRun;
- считает статистику;
- пишет статистику;
- готовит UI;
- форматирует пользовательские строки.

Предпочтительная схема:

Check flow
→ CheckHistoryRepository.saveCheckRun(...)
→ LocalStatisticsWriter.onCheckRunSaved(...)
→ CheckStatisticsRepository.update(...)
→ локальное хранилище статистики

Дополнительно:

CheckHistoryRepository.getRecentCheckRuns(...)
→ LocalStatisticsRebuilder.rebuildFromHistory(...)
→ CheckStatisticsRepository.replaceAll(...)

Названия можно адаптировать под существующую архитектуру проекта.

## Что считать успехом

Нужно аккуратно определить, что считается success/failure.

Используй existing status-модели из v0.8.0, если они есть.

Общий смысл:

- CheckRun SUCCESS → успешная проверка.
- CheckRun PARTIAL_FAILURE → частично успешная проверка.
- CheckRun FAILURE → ошибочная проверка.
- CheckRun CANCELLED → отменённая проверка, не должна искажать successRate как обычная ошибка, если в проекте принято иначе — следуй текущей модели.
- CheckTargetResult SUCCESS → успешная проверка target.
- CheckTargetResult FAILURE/TIMEOUT/DNS_ERROR/CONNECTION_ERROR/TLS_ERROR → неуспешная проверка target.
- CheckTargetResult SKIPPED/CANCELLED → считать отдельно или исключать из successRate, если так логичнее для текущей модели.

Не хранить всё одной строкой "error". Ошибки должны быть типами, enum или кодами.

## Формулы

Процент успеха считать безопасно:

successRate = successCount / totalCount

Если totalCount == 0, не делить на ноль.

В таком случае вернуть:

- 0;
- null;
- UNKNOWN;

Выбери вариант, который лучше соответствует текущей модели проекта.

Среднюю задержку считать только по записям, где latencyMs доступна и валидна.

Если latencyMs отсутствует, не подставлять магический ноль, если это исказит статистику.

LocalStatisticsWriter

1. Принять завершённый CheckRun и связанные CheckTargetResult.
2. Обновить агрегаты.
3. Не заниматься UI.

## Rebuild статистики

Добавь возможность пересобрать статистику из истории.

Это нужно для случаев:

- миграция модели статистики;
- повреждение статистических агрегатов;
- отладка;
- будущая кнопка "пересчитать статистику";
- тесты.

Минимальный смысл:

1. Очистить текущие агрегаты.
2. Прочитать сохранённые CheckRun и CheckTargetResult.
3. Последовательно пересчитать агрегаты.
4. Сохранить новый результат.
5. Не удалить историю проверок.

Rebuild не должен быть UI-функцией в v0.8.1. Это внутренний метод/use case/repository operation.

## Retention policy

Если статистика хранится по дням, она не должна расти бесконечно.

Допустимые варианты:

- хранить daily statistics за последние 30 дней;
- хранить столько же, сколько хранится check history;
- хранить агрегаты all-time плюс daily за ограниченный период.

Требования:

1. Значения вынести в именованные константы.
2. Не оставлять магические числа внутри методов.
3. Cleanup статистики не должен ломать общую all-time статистику.
4. Cleanup должен быть согласован с cleanup истории из v0.8.0.

## Интеграция с v0.8.0

Подключить статистику после успешного сохранения CheckRun.

Требования:

1. Если CheckRun успешно сохранён, обновить статистику.
2. Если статистику сохранить не удалось, не ломать текущий результат проверки.
3. Ошибка записи статистики не должна ломать главный экран.
4. Ошибка записи статистики должна быть залогирована как diagnostic/debug error без секретов.
5. Last check state из v0.7.2 и history из v0.8.0 не должны сломаться.
6. Не менять алгоритм проверки endpoint'ов без необходимости.

## Ошибки

Ошибки статистики должны быть обработаны явно.

Если статистику не удалось обновить:

1. Не отменять сохранение CheckRun, если оно уже выполнено.
2. Не ломать главный экран.
3. Не падать приложением.
4. Записать техническую ошибку в лог без секретов.
5. Подготовить основу для будущей диагностики.

Не проглатывать ошибки молча.

## Приватность и безопасность

Не сохранять лишние чувствительные данные.

Запрещено сохранять:

- номер телефона;
- IMSI;
- IMEI;
- точные координаты без явной необходимости;
- токены;
- секреты;
- приватные URL, если они не должны быть видны пользователю;
- содержимое заголовков авторизации;
- любые данные, которые могут раскрыть личность пользователя без необходимости.

Статистика должна агрегировать уже локально сохранённые безопасные данные.

В v0.8.1 не добавлять отправку данных наружу.

## Тесты

1. После одного успешного CheckRun totalRuns == 1 и successRuns == 1.
2. После одного ошибочного CheckRun totalRuns == 1 и failureRuns == 1.

10. consecutiveFailureCount сбрасывается после успеха.
11. TargetStatistics обновляется по targetId.
12. RouteKindStatistics обновляется по routeKind.
13. NetworkStatistics обновляется по networkType/operator.
14. DailyCheckStatistics обновляется по дате проверки.
15. Rebuild статистики из истории даёт тот же результат, что последовательное обновление.

## Ручное тестирование

Проверить вручную на устройстве или эмуляторе:

1. Обновиться с v0.8.0.
   Ожидается: приложение запускается, главный экран работает.

2. Выполнить успешную проверку.
   Ожидается: CheckRun сохраняется, общая статистика обновляется.

3. Выполнить ошибочную проверку.
   Ожидается: ошибка сохраняется в истории, статистика ошибок обновляется.

4. Выполнить несколько проверок подряд.
   Ожидается: totalRuns, successRuns, failureRuns и partialFailureRuns обновляются корректно.

5. Проверить статистику по endpoints/targets.
   Ожидается: каждый target имеет свои счётчики и дату последней проверки.

6. Проверить статистику по routeKind.
   Ожидается: разные routeKind не смешиваются.

7. Проверить статистику по networkType/operator.
   Ожидается: разные network/operator-значения не смешиваются.

8. Проверить daily statistics.
   Ожидается: проверки текущего дня попадают в правильный daily bucket.

9. Перезапустить приложение.
   Ожидается: статистика не пропадает.

10. Запустить rebuild статистики из истории, если есть внутренний способ.
   Ожидается: агрегаты пересчитываются без потери истории.

11. Проверить главный экран.
   Ожидается: last check state из v0.7.2 и history из v0.8.0 не сломаны.

12. Проверить поведение при ошибке storage.
   Ожидается: приложение не падает, результат текущей проверки не ломается.

13. Проверить логи.
   Ожидается: в логах нет токенов, секретов, номеров телефонов, IMSI, IMEI и лишних приватных данных.
