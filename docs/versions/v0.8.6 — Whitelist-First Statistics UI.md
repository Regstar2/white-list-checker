## Контекст

В v0.8.0-v0.8.3 была добавлена и стабилизирована техническая история проверок:

- CheckRun.
- CheckTargetResult.
- statistics writer.
- rebuild.
- cleanup.
- diagnostics.
- consistency checks.

В v0.8.4 была добавлена статистика белых списков:

- доступность целей;
- включения/выключения;
- доступность по дням;
- target availability;
- графики/бар-индикаторы.

В v0.8.5 исправлялось отображение статистики и смысловые противоречия.

Теперь нужно изменить продуктовый акцент:

Экран “Статистика” должен быть посвящён в первую очередь белым спискам, а не техническим проверкам. Пользователю важнее видеть:

- какие белые списки доступны;
- когда они появились;
- когда исчезли;
- как часто включались/выключались;
- какие цели стабильные;
- какие цели нестабильные;
- как менялась доступность по дням.

Техническая статистика проверок нужна, но не как главный пользовательский экран. Её нужно сократить до минимума и/или перенести в логи/диагностику.

## Главная цель версии

Сделать экран “Статистика” whitelist-first:

- оставить на нём только статистику, посвящённую белым спискам и доступности целей;
- техническую статистику проверок сократить до минимального summary;
- подробные данные о проверках вынести в логи, diagnostics или скрытый технический блок;
- не сломать историю проверок, потому что она нужна для rebuild whitelist availability statistics.

## Важное решение

Не удалять техническую историю проверок из data/domain слоя.

CheckRun и CheckTargetResult нужны для:

- последнего результата на главном экране;
- rebuild статистики белых списков;
- диагностики;
- логов;
- расследования ошибок;
- будущих multi-device reports.

Нужно убрать техническую статистику проверок из основного пользовательского экрана статистики, а не вырезать её из приложения полностью.

## Новая структура экрана “Статистика”

Экран “Статистика” должен быть примерно таким:

1. Header / актуальность данных.
2. Summary белых списков.
3. Текущее состояние целей.
4. График доступности по дням.
5. График включений/выключений.
6. Последние изменения.
7. Стабильные / нестабильные цели.
8. Ссылка или сворачиваемый блок “Технические данные проверок”, если нужно.

## Header

Верхняя карточка должна быть компактной.

Показывать:

- “Обновлено: только что”.
- “Последняя проверка: завершена / частично / ошибка”.
- “Проверено целей: X/Y”.
- Если данных мало: “Данных пока мало”.

Не показывать большую пустую карточку.

## Главный блок “Белые списки”

Показать:

- доступно сейчас;
- недоступно сейчас;
- неизвестно;
- процент доступности;
- последнее включение;
- последнее выключение;
- изменений за период.

Пример:

Белые списки

- Доступно сейчас: 6
- Недоступно: 1
- Неизвестно: 1
- Доступность: 85.7%
- Включений: 6
- Выключений: 1
- Последнее включение: только что
- Последнее выключение: только что

## Блок “Текущее состояние целей”

Показать список целей компактно:

- VK — недоступно / ошибка / unknown.
- GitHub — доступно.
- Wikipedia — доступно.
- Yandex — доступно.
- Mail.ru — доступно.

Требования:

1. Не показывать сырые URL в основном списке.
2. Использовать безопасный display label.
3. Использовать status chips или компактные status labels.
4. Не делать огромные карточки на каждую цель.
5. Если целей много, показывать top N + “Показать все”.
6. Если есть разные категории целей, можно группировать, но без большого refactor.

## Блок “Доступность по дням”

Показывать только whitelist availability.

Требования:

1. Значения процентов отображать с `%`.
2. Если есть только одна точка, не делать вид, что это полноценный график.
3. При одной точке показать:
   - “Сегодня: 85.7%”.
   - “Недостаточно данных для динамики”.
4. Если данных несколько дней, показать простой график/бар-индикаторы.
5. Не показывать technical check success rate в этом блоке.

## Блок “Включения и выключения”

Показывать изменения whitelist, а не technical failures.

Требования:

1. Включения и выключения показывать отдельно.
2. Count values не отображать как проценты.
3. Если включений/выключений мало, использовать компактный список.
4. Если данных недостаточно, показать fallback:
   - “Недостаточно данных для графика изменений”.
5. Не делать misleading bars, где count = 1 выглядит как 100%.

## Блок “Последние изменения”

Добавить или использовать существующий список последних availability events.

Показать последние 5–10 событий:

- GitHub стал доступен — только что.
- VK стал недоступен — 5 мин назад.
- Cloudflare неизвестно — 10 мин назад.

Требования:

1. Показывать только whitelist availability events.
2. Не показывать технические timeout/DNS errors как “выключение whitelist”, если это не достоверное исчезновение.
3. Для ошибок использовать “результат неизвестен”, если это техническая ошибка проверки.
4. Если событий нет, показать:
   - “Изменений пока нет”.
   - “Выполните несколько проверок, чтобы увидеть динамику”.

## Блок “Стабильные и нестабильные цели”

Показать:

- стабильные цели;
- нестабильные цели.

Требования:

1. Если все значения одинаковые, не делать ложный рейтинг.
2. Если данных мало, показать “Недостаточно данных для рейтинга”.
3. Значения доступности показывать как проценты.
4. Нестабильность показывать как количество изменений:
   - “1 изменение”;
   - “2 изменения”;
   - “5 изменений”.
5. Не показывать всем targets полный bar, если у всех score = 1.

## Formatting rules

Проверить и использовать единый formatter слой.

Нужны единые функции/методы по смыслу:

- formatPercent(value).
- formatCount(value).
- formatDurationMs(value).
- formatRelativeTime(value).
- formatDate(value).
- formatTargetLabel(value).
- formatEndpointLabel(value).
- formatWhitelistState(value).
- formatWhitelistTransition(value).
- formatTechnicalCheckStatus(value).

Требования:

1. Percent:
   - `0%`;
   - `40.2%`;
   - `85.7%`;
   - `100%`;
   - не показывать `NaN%`;
   - не показывать `Infinity%`.
2. Count:
   - `1 изменение`;
   - `2 изменения`;
   - `5 изменений`;
   - `6 включений`;
   - `1 выключение`.
3. Unknown:
   - “Нет данных”;
   - “Неизвестно”;
   - “Недостаточно данных”.
4. URL:
   - в основном UI не показывать;
   - если нужно в деталях, показывать безопасный host без query params и credentials.

- номер телефона;
- IMSI;
- IMEI;
- точные координаты;
- токены;
- секреты;
- приватные URL, если они не должны быть видны пользователю;

- заголовки авторизации;

1. Скрывать query params.

3. Скрывать tokens/secrets.
4. В обычном UI показывать только безопасное имя или host.
5. Полный URL показывать только в diagnostics/logs, если это безопасно.

# v0.8.6 — Whitelist-First Statistics UI

## Цель

Сделать экран статистики ориентированным на белые списки и доступность целей, а техническую статистику проверок сократить или вынести в логи/диагностику.

## Входит в версию

- Перестройка экрана статистики вокруг whitelist availability.
- Удаление большой технической статистики проверок из основного Statistics UI.
- Минимальный technical summary только для актуальности данных.
- Перенос подробных check statistics в logs/diagnostics/collapsed technical block.
- Компактная карточка статистики на главном экране.
- Блок текущего состояния целей.
- Блок последних изменений whitelist availability.
- Улучшение графиков доступности и включений/выключений.
- Безопасные display labels для целей/endpoints.
- Обновление пользовательских строк.
- Обновление ручного test plan.

## Не входит в версию

- Worker.
- Telegram Bot.
- Multi-device reports.
- Отправка данных наружу.
- Экспорт статистики.
- Сложные фильтры.
- Прогнозирование.
- Репутация источников.
- Удаление CheckRun/CheckTargetResult.
- Полная переработка архитектуры статистики.
- Изменение check/proxy/routing logic.
- Добавление тяжёлой chart-библиотеки без необходимости.

## Архитектурные ограничения

- История проверок остаётся в data/domain слое.
- Check statistics остаётся доступной для logs/diagnostics/rebuild.
- Основной Statistics UI показывает whitelist availability, а не технические check metrics.
- UI не должен считать статистику сам.
- Пользовательские строки вынести в ресурсы.
- Endpoint labels должны быть безопасными.
- Не показывать и не логировать чувствительные данные.
- Не добавлять функции будущих версий.


На Windows:

```powershell

```

## Ручное тестирование

Проверить вручную на устройстве или эмуляторе:

1. Обновиться с v0.8.5.
   Ожидается: приложение запускается, старая история и whitelist statistics не потеряны.

2. Открыть главный экран.
   Ожидается: статистика на главном экране показывает whitelist summary, а не total check runs/success rate/error streak.

3. Открыть экран “Статистика”.
   Ожидается: экран посвящён белым спискам и доступности целей.

4. Проверить верхнюю карточку.
   Ожидается: есть актуальность данных и последняя проверка, но нет большой technical check statistics.

5. Проверить блок “Белые списки”.
   Ожидается: доступны значения доступно/недоступно/неизвестно/доступность/включения/выключения.

6. Проверить блок “Текущее состояние целей”.
   Ожидается: цели отображаются компактно, без сырых URL.

7. Проверить блок “Последние изменения”.
   Ожидается: показываются whitelist availability events, а не технические ошибки проверки как исчезновения whitelist.

8. Проверить график доступности по дням.
   Ожидается: проценты отображаются с `%`.

9. Проверить график включений/выключений.
   Ожидается: counts не выглядят как проценты.

10. Проверить стабильные/нестабильные цели.
    Ожидается: при малом количестве данных нет ложного рейтинга.

11. Проверить доступ к техническим данным проверок.
    Ожидается: они доступны в логах/diagnostics/collapsed block, но не занимают основной Statistics UI.

12. Проверить endpoint details.
    Ожидается: сырые URL не видны в основном UI, query params/secrets не отображаются.

13. Проверить тёмную тему.
    Ожидается: UI читается нормально.

14. Проверить светлую тему.
    Ожидается: UI читается нормально.

15. Проверить маленький экран.
    Ожидается: карточки не обрезаются, labels не ломают layout.

16. Проверить крупный системный шрифт, если возможно.
    Ожидается: UI остаётся usable.

17. Проверить состояние без данных.
    Ожидается: понятный empty state.

18. Проверить состояние с одной точкой графика.
    Ожидается: insufficient-data state или компактное отображение без misleading chart.

19. Проверить работу без сети.
    Ожидается: статистика не ломается, техническая ошибка не считается ложным выключением whitelist.

20. Проверить endpoint timeout/DNS error.
    Ожидается: whitelist availability UI не ломается.

21. Перезапустить приложение.
    Ожидается: статистика отображается так же, данные не потеряны.

22. Проверить rebuild whitelist statistics, если есть diagnostics-кнопка.
    Ожидается: rebuild работает, история проверок не удаляется.

23. Проверить логи.
    Ожидается: нет токенов, секретов, IMSI, IMEI, номера телефона, точных координат и приватных URL.
