# Cursor prompt: Whitelist Checker Android MVP v0.3

Доработай Android-приложение Whitelist Checker с версии v0.2 до v0.3.

Главная цель v0.3: приложение должно не просто показывать текущий статус проверки, а отслеживать подтверждённое изменение состояния белых списков.

Нужно реализовать локальное хранение последнего подтверждённого состояния и антидребезг: новый статус должен подтвердиться несколько раз подряд, прежде чем приложение посчитает, что состояние действительно изменилось.

Telegram, proxy, WorkManager и фоновые проверки пока НЕ добавлять. Сейчас только логика отслеживания смены состояния внутри приложения. Не надо тащить весь зоопарк сразу, мы пока строим фундамент, а не торговый центр из костылей.

## 2. Цель v0.3

Приложение должно:

1. После каждой ручной проверки получать текущий `WhitelistState`.
2. Сравнивать его с последним подтверждённым состоянием.
3. Не считать состояние изменившимся сразу после одной проверки.
4. Требовать подтверждение одного и того же нового состояния 2 раза подряд.
5. Если новый статус подтвердился 2 раза подряд:
   - обновить `lastConfirmedState`;
   - создать событие смены состояния;
   - показать это событие на экране.
6. Отслеживать только важные переходы:
   - `WHITELIST_OFF → WHITELIST_ON`;
   - `WHITELIST_ON → WHITELIST_OFF`.
7. Остальные переходы сохранять как подтверждённое состояние, но не считать событием включения/выключения БС.
8. Сохранять состояние между перезапусками приложения.
9. Не добавлять Telegram.
10. Не добавлять фоновые проверки.
11. Не добавлять историю всех проверок.
12. Не добавлять Room.
13. Не добавлять WorkManager.

```kotlin
private fun parseWhitelistState(value: String?): WhitelistState {
    if (value.isNullOrBlank()) {
        return WhitelistState.UNKNOWN
    }

    return runCatching {
        WhitelistState.valueOf(value)
    }.getOrDefault(WhitelistState.UNKNOWN)
}
```

## 8. Логика антидребезга

Правило:

```text
Новый статус должен подтвердиться 2 раза подряд.
```

Создай константу:

```kotlin
private const val REQUIRED_CONFIRMATION_COUNT = 2
```

Алгоритм:

```text
1. Если currentState == UNKNOWN:
   - не менять lastConfirmedState;
   - сбросить pendingState в UNKNOWN;
   - pendingStateCount = 0;
   - event = null.

2. Если lastConfirmedState == UNKNOWN:
   - сразу принять currentState как первое подтверждённое состояние;
   - lastConfirmedState = currentState;
   - lastConfirmedAtMillis = nowMillis;
   - pendingState = UNKNOWN;
   - pendingStateCount = 0;
   - event = null.
   Это начальная фиксация, а не событие включения/выключения.

3. Если currentState == lastConfirmedState:
   - состояние не изменилось;
   - pendingState = UNKNOWN;
   - pendingStateCount = 0;
   - event = null.

4. Если currentState != lastConfirmedState:
   - если currentState == pendingState:
       pendingStateCount += 1
     иначе:
       pendingState = currentState
       pendingStateCount = 1

5. Если pendingStateCount < REQUIRED_CONFIRMATION_COUNT:
   - не менять lastConfirmedState;
   - event = null.

6. Если pendingStateCount >= REQUIRED_CONFIRMATION_COUNT:
   - oldState = lastConfirmedState;
   - newState = currentState;
   - обновить lastConfirmedState = currentState;
   - lastConfirmedAtMillis = nowMillis;
   - lastStateChangeAtMillis = nowMillis;
   - pendingState = UNKNOWN;
   - pendingStateCount = 0;
   - создать event.
```

## 9. Тип события

Определи тип события так:

```kotlin
private fun resolveChangeType(
    oldState: WhitelistState,
    newState: WhitelistState
): WhitelistStateChangeType {
    if (oldState == WhitelistState.WHITELIST_OFF
            && newState == WhitelistState.WHITELIST_ON) {
        return WhitelistStateChangeType.WHITELIST_TURNED_ON
    }

    if (oldState == WhitelistState.WHITELIST_ON
            && newState == WhitelistState.WHITELIST_OFF) {
        return WhitelistStateChangeType.WHITELIST_TURNED_OFF
    }

    return WhitelistStateChangeType.OTHER_CONFIRMED_CHANGE
}
```

В v0.3 событие `OTHER_CONFIRMED_CHANGE` можно показывать в UI, но потом Telegram будет отправляться только для:

```text
WHITELIST_TURNED_ON
WHITELIST_TURNED_OFF
```

## 10. Обновить WhitelistCheckUseCase или создать отдельный MonitorUseCase

Лучше создать отдельный use case:

```kotlin
class WhitelistMonitorUseCase
```

Ответственность:

```text
1. Выполнить обычную проверку через WhitelistCheckUseCase.
2. Получить текущий WhitelistState из результата проверки.
3. Прочитать WhitelistMonitorState из MonitorStateRepository.
4. Передать currentState и savedState в StateChangeDetector.
5. Сохранить updatedMonitorState.
6. Вернуть единый результат для UI.
```

Добавь модель:

```kotlin
data class WhitelistMonitorResult(
    val checkResult: NetworkCheckResult,
    val monitorState: WhitelistMonitorState,
    val stateChangeEvent: WhitelistStateChangeEvent?
)
```

Метод:

```kotlin
suspend fun checkAndUpdateState(): WhitelistMonitorResult
```

Важно:

```text
WhitelistCheckUseCase должен остаться ответственным только за сетевую проверку.
WhitelistMonitorUseCase отвечает за состояние мониторинга.
```

Не смешивай всё в один класс, иначе через две версии там будет болото, а потом сам же будешь спрашивать, почему Cursor всё сломал.

## 20. Требования к качеству

Обязательно:

```text
1. Проект должен компилироваться.
2. Не оставлять TODO вместо рабочей логики.
3. Состояние должно сохраняться между перезапусками приложения.
4. DataStore должен безопасно обрабатывать пустые и неизвестные значения.
5. Антидребезг должен требовать 2 одинаковых новых статуса подряд.
6. Начальное UNKNOWN-состояние не должно создавать событие включения/выключения БС.
7. Возврат к lastConfirmedState должен сбрасывать pending-состояние.
8. UI не должен падать при null monitorState.
9. UI не должен падать при null stateChangeEvent.
10. Сетевые проверки должны продолжать выполняться только через cellular Network.
11. Не использовать bindProcessToNetwork.
12. Не использовать activeNetwork для проверки сайтов.
```

## 21. Acceptance criteria

После выполнения v0.3 должно работать так:

```text
1. Пользователь открывает приложение.
2. Приложение показывает последнее подтверждённое состояние, если оно уже было сохранено.
3. Пользователь нажимает "Проверить мобильную сеть".
4. Приложение выполняет проверку как в v0.2.
5. Приложение показывает текущий результат проверки.
6. Приложение обновляет состояние мониторинга.
7. Если новый статус отличается от подтверждённого только 1 раз, приложение показывает pending-состояние 1/2.
8. Если новый статус повторился 2 раза подряд, приложение обновляет подтверждённое состояние.
9. Если переход был WHITELIST_OFF → WHITELIST_ON, приложение показывает событие "Белые списки включились".
10. Если переход был WHITELIST_ON → WHITELIST_OFF, приложение показывает событие "Белые списки выключились".
11. Если состояние вернулось к старому до подтверждения, pending-состояние сбрасывается.
12. После перезапуска приложения последнее подтверждённое состояние сохраняется.
```

## 22. Финальная задача

Доработай проект до v0.3.

Сохрани существующую проверку мобильной сети из v0.2, но добавь слой мониторинга состояния:

```text
WhitelistCheckUseCase
    ↓
WhitelistMonitorUseCase
    ↓
StateChangeDetector
    ↓
MonitorStateRepository/DataStore
    ↓
MainViewModel/MainScreen
```

После изменений проект должен компилироваться, запускаться и корректно отслеживать подтверждённое включение/выключение белых списков.
