## Контекст

В версии v0.7.2 была исправлена логика отображения последней проверки на главном экране.

Теперь нужно подготовить фундамент для будущей статистики: приложение должно сохранять результаты завершённых проверок локально в нормальной структурированной форме.

Важно: v0.8.0 — это не экран статистики и не аналитика. Это только слой сохранения истории проверок и минимальная интеграция с текущим check flow.

## Проблема

Сейчас приложение показывает последнее состояние проверки, но нет полноценного локального основания для будущей статистики.

Нужно перестать опираться только на временное состояние, логи или один last-check snapshot. Каждая завершённая проверка должна сохраняться как отдельный check run с результатами по целям проверки.

## Цель версии

Добавить локальное сохранение результатов проверок.

После реализации приложение должно:

1. Создавать запись CheckRun при завершении проверки.
2. Сохранять результаты отдельных endpoint/target-проверок как CheckTargetResult.
3. Позволять читать последние check runs из repository.
4. Не ломать главный экран и последнюю проверку.
5. Не добавлять UI статистики.
6. Не отправлять данные наружу.
7. Подготовить чистую основу для v0.8.1 Local Statistics Writer.

## Входит в версию

Реализовать только persistence foundation:

1. Найти текущий check flow.
2. Найти, где формируется результат проверки.

4. Добавить domain-модели для истории проверок.
5. Добавить data/entity-модели для локального хранения, если в проекте есть БД/Room.

9. Добавить чтение последних записей для диагностики/будущей статистики.
10. Добавить cleanup/retention policy, чтобы история не росла бесконечно.

## Требуемая модель данных

Добавь или адаптируй модели по смыслу.

### CheckRun

CheckRun — это одна завершённая проверка.

Минимальные поля по смыслу:

- id.
- startedAt.
- finishedAt.
- durationMs.
- triggerType.
- networkType.
- operatorName или operatorCode, если это уже доступно.
- routeMode.
- overallStatus.
- successCount.
- failureCount.
- skippedCount, если в проекте есть skipped-состояния.
- appVersion.
- schemaVersion.
- createdAt.

Допустимые значения overallStatus по смыслу:

- SUCCESS.
- PARTIAL_FAILURE.
- FAILURE.
- CANCELLED.
- UNKNOWN.

Если в проекте уже есть свои status-типы, используй их или аккуратно сделай mapper.

### CheckTargetResult

CheckTargetResult — это результат проверки отдельной цели внутри CheckRun.

Минимальные поля по смыслу:

- id.
- checkRunId.
- targetId или endpointId.
- targetLabel или endpointLabel, если безопасно хранить.
- targetHost или targetUrl, если это уже используется и не содержит секретов.
- routeKind.
- status.
- latencyMs.
- httpStatusCode, если применимо.
- errorCode.
- errorCategory.
- startedAt.
- finishedAt.
- createdAt.

Допустимые status по смыслу:

- SUCCESS.
- FAILURE.
- TIMEOUT.
- DNS_ERROR.
- CONNECTION_ERROR.
- TLS_ERROR.
- CANCELLED.
- SKIPPED.
- UNKNOWN.

Не обязательно вводить все статусы, если в проекте уже есть готовая модель. Главное — не хранить всё одной строкой "error".

## Слои и ответственность

Соблюдай разделение ответственности.

Предпочтительная схема:

Repository/storage
→ local data source
→ mapper
→ domain repository
→ check completion use case
→ текущий check flow

Не складывать всё в один класс.

Не делать один класс, который одновременно:

- слушает проверку;
- считает итог;
- пишет в БД;
- чистит историю;
- маппит entity;
- готовит UI.

## Repository

Добавь repository по смыслу:

CheckHistoryRepository или CheckRunRepository.

Минимальные методы по смыслу:

- saveCheckRun(checkRun, targetResults)
- getLatestCheckRun()
- getRecentCheckRuns(limit)
- deleteOldCheckRuns(olderThan или keepLast)
- deleteAllCheckRuns(), только если в проекте уже есть сценарий сброса данных или это нужно для тестов.

Не делай методы public без необходимости.

Если в проекте есть интерфейсы repository в domain-слое — добавь интерфейс туда и реализацию в data-слой.

Если архитектура проекта проще — сделай минимально, но не смешивай UI и storage.

## Storage

Используй существующий механизм хранения проекта.

Если уже используется Room:

1. Добавь entity для check_runs.
2. Добавь entity для check_target_results.
3. Добавь DAO.
4. Добавь миграцию, если база уже имеет версию.
5. Не ломай существующие таблицы.
6. Не удаляй данные пользователя.

Если используется DataStore:

1. DataStore подходит для last state и настроек, но плохо подходит для истории многих записей.
2. Если истории будет много, лучше использовать Room/SQLite.
3. Не запихивай массив большой истории в preferences DataStore без причины.

Если используется файл-хранилище:

1. Сохраняй структурированный JSON.
2. Не переписывай весь файл слишком часто, если это может стать проблемой.
3. Добавь защиту от повреждённого файла.
4. Добавь cleanup.

Если storage ещё нет:

1. Не тащи тяжёлую новую инфраструктуру без оценки.
2. Для Android-проекта предпочтительно использовать Room, если в проекте уже принят Android Jetpack stack.
3. Если добавление Room слишком большое для этой версии, сделай минимальную file-based реализацию и зафиксируй ограничение в docs/versions/v0.8.0.md.
4. Не добавляй новый storage только ради красоты.

## Retention policy

История не должна расти бесконечно.

Добавь простой retention policy.

Допустимые варианты:

- хранить последние 100 или 200 check runs;
- хранить записи за последние 7 или 14 дней;
- комбинированно: keepLastRuns + maxAgeDays.

Требования:

1. Значения вынести в именованные константы.
2. Не оставлять магические числа внутри методов.
3. Cleanup выполнять после успешного сохранения нового check run или в уже существующем maintenance-механизме.
4. Cleanup не должен удалять последнюю проверку, если других данных нет.

## Интеграция с текущим check flow

Нужно подключить запись истории в момент, когда проверка уже завершена и итоговый результат известен.

Требования:

1. Не менять сам алгоритм проверки endpoint'ов без необходимости.
2. Не замедлять UI-поток.
3. Не падать, если сохранение истории завершилось ошибкой.
4. Ошибка сохранения истории не должна отменять сам результат проверки.
5. Ошибку сохранения можно логировать как diagnostic/debug error без приватных данных.
6. Last check state должен продолжать обновляться как раньше.
7. Если возможно, last check state и check history должны использовать один и тот же нормализованный результат, чтобы не было расхождений.

## Ошибки

Ошибки хранения должны быть обработаны явно.

Если check run не удалось сохранить:

1. Не ломать главный экран.
2. Не ломать результат текущей проверки.
3. Записать техническую ошибку в лог без секретов.
4. Не показывать пользователю лишнюю ошибку, если в текущем UI нет места для такой диагностики.
5. Подготовить основу, чтобы в будущем диагностика могла показать проблему хранения.

Не проглатывать ошибки молча.

## Приватность и безопасность

Не сохранять лишние чувствительные данные.

Запрещено сохранять:

- номер телефона;
- IMSI;
- IMEI;
- точные координаты без явной необходимости;
- токены;
- секреты;
- приватные URL, если они не должны быть видны пользователю;
- содержимое заголовков авторизации;
- любые данные, которые могут раскрыть личность пользователя без необходимости.

Если сохраняются network/operator/cell-поля, они должны быть минимальными и обоснованными для будущей статистики.

В v0.8.0 не добавлять отправку данных наружу.

## Ручное тестирование

Проверить вручную на устройстве или эмуляторе:

1. Обновиться с v0.7.2.
   Ожидается: приложение запускается, главный экран работает.

2. Выполнить успешную проверку.
   Ожидается: результат проверки сохраняется в истории.

4. Выполнить несколько проверок подряд.
   Ожидается: каждая завершённая проверка создаёт отдельный CheckRun.

5. Проверить результаты отдельных endpoints/targets.
   Ожидается: они связаны с правильным CheckRun.

6. Перезапустить приложение.
   Ожидается: история проверок не пропадает.

7. Проверить главный экран.
   Ожидается: последняя проверка отображается как в v0.7.2, stale-state не сломан.

8. Проверить поведение при ошибке storage.
   Ожидается: результат проверки не теряется для UI, приложение не падает.

9. Проверить cleanup.
   Ожидается: история не растёт бесконечно, старые записи удаляются по выбранной политике.

10. Проверить логи.
   Ожидается: в логах нет токенов, секретов, номеров телефонов, IMSI, IMEI и лишних приватных данных.

## Ограничения diff

Не принимать большой расползающийся diff.

Если для добавления persistence понадобилось изменить много файлов, сначала остановись и проверь:

1. Не началась ли реализация статистики.
2. Не появился ли экран статистики.
3. Не добавился ли Worker.
4. Не добавился ли Telegram Bot.
5. Не переписывается ли check algorithm.
6. Не переписывается ли главный экран.
7. Не меняется ли routing/proxy logic без необходимости.
8. Не добавляются ли зависимости без явной пользы.
9. Не появились ли классы с неясной ответственностью.
10. Не нарушено ли разделение UI/domain/data.

Если diff стал слишком большим, уменьши scope и сделай только фундамент сохранения check results.

## Формат отчёта после выполнения

В конце работы напиши отчёт:

1. Что было найдено в текущем check flow.
2. Как теперь сохраняется CheckRun.
3. Как теперь сохраняются CheckTargetResult.
4. Где находится repository.
5. Какая storage-реализация использована и почему.
6. Какая retention policy выбрана.
7. Какие файлы изменены.
8. Какие тесты добавлены или обновлены.
9. Какие команды проверки выполнены.
10. Какие проверки не удалось выполнить и почему.
11. Что нужно проверить вручную на телефоне.
12. Есть ли риски или ограничения после v0.8.0.
13. Что подготовлено для v0.8.1 Local Statistics Writer.

## Критерии готовности v0.8.0

Версия считается готовой только если:

- завершённая проверка сохраняется локально;
- CheckRun содержит время начала, время завершения, итоговый статус и контекст проверки;
- CheckTargetResult содержит результаты отдельных endpoints/targets;
- target results связаны с check run;
- есть repository для истории проверок;
- есть cleanup/retention policy;
- last check state из v0.7.2 не сломан;
- главный экран работает как раньше;
- нет экрана статистики;
- нет Worker;
- нет Telegram Bot;
- нет отправки данных наружу;
- не сохраняются секреты и чувствительные данные;
- пользовательские строки не хардкодятся;
- domain/data/UI не смешаны без необходимости;
- логика покрыта тестом или описан ручной тест;
- проект собирается;
- CHANGELOG обновлён;
- в отчёте указано, что проверить вручную.
