# Персональный путь разработки приложения: от идеи до релиза

Документ описывает рабочий маршрут разработки для моих проектов: Android-приложений, desktop/web-проектов, Java-работ, утилит, сервисов и проектов с активным использованием Cursor/Codex.

Главная цель: не просто “начать проект”, а довести его до работающей версии, релиза и поддержки. Потому что начать проект умеет каждый. Закончить — уже почти незаконное колдовство.

---

## 0. Главный принцип маршрута

Разработка должна идти не хаотично, а через версии.

```text
Одна версия = одна понятная цель.
Один промпт для AI = одна ограниченная задача.
Один этап = один проверяемый результат.
```

Запрещено начинать с огромного промпта в стиле:

```text
Сделай мне всё приложение целиком красиво, правильно, архитектурно и чтобы работало.
```

Это не техническое задание, а записка в бутылке.

Правильный подход:

```text
v0.1.0 — минимальный каркас приложения
v0.2.0 — основной сценарий без полировки
v0.3.0 — сохранение данных
v0.4.0 — уведомления / синхронизация / интеграции
v0.5.0 — настройки и устойчивость
v0.9.0 — подготовка к релизу
v1.0.0 — первый стабильный релиз
```

## 1. Этап идеи

### Цель

Понять, что именно я хочу сделать и зачем это вообще нужно.

На этом этапе нельзя сразу писать код. Да, очень хочется. Нет, не надо. Именно так появляются проекты, где есть красивый splash screen, но нет смысла существования.

### Нужно ответить

```text
1. Какую проблему решает приложение?
2. Для кого оно?
3. Что пользователь делает в приложении чаще всего?
4. Что является главным сценарием?
5. Почему это не проще сделать уже существующим инструментом?
6. Что будет считаться успехом первой версии?
7. Что точно НЕ входит в первую версию?
```

### Результат этапа

Создать файл:

```text
docs/product/idea.md
```

Минимальная структура:

```markdown
# Идея проекта

## Проблема

## Целевая аудитория

## Главный пользовательский сценарий

## Почему это приложение имеет смысл

## Что входит в MVP

## Что не входит в MVP

## Риски

## Критерий успеха первой версии
```

### Правило выхода

Нельзя переходить к архитектуре, пока нельзя одной фразой объяснить проект.

Плохо:

```text
Ну это приложение для всякого, чтобы удобнее было.
```

Лучше:

```text
Приложение проверяет состояние источников белых списков и уведомляет пользователя, если доступность изменилась.
```

## 2. Этап проверки смысла

### Цель

Понять, стоит ли проект делать.

Не каждый проект заслуживает жизни. Некоторые идеи должны умереть в `ideas.md`, и это нормально. Цифровая эвтаназия иногда гуманнее, чем ещё один заброшенный репозиторий.

### Проверить

```text
1. Есть ли аналоги?
2. Чем они плохи?
3. Что моё приложение делает лучше?
4. Можно ли сделать MVP быстро?
5. Есть ли технические блокеры?
6. Есть ли юридические/платформенные ограничения?
7. Буду ли я сам этим пользоваться?
```

### Для моих проектов особенно важно

```text
1. Работает ли это в России?
2. Не завязано ли решение на недоступные сервисы?
3. Можно ли обойтись без собственного сервера на старте?
4. Можно ли сделать локальный режим?
5. Можно ли тестировать на моём телефоне/ПК?
6. Не требует ли MVP слишком сложного стека?
```

### Результат этапа

Создать файл:

```text
docs/research/market-and-feasibility.md
```

Минимальная структура:

```markdown
# Проверка смысла проекта

## Аналоги

## Что в аналогах плохо

## Моё отличие

## Техническая реализуемость

## Ограничения

## Риски

## Решение

- [ ] Делаю MVP
- [ ] Откладываю
- [ ] Убиваю идею
```

### Правило выхода

Если отличие от аналогов нельзя сформулировать, проект пока не начинать.

## 3. Этап ограничения MVP

### Цель

Сильно сузить первую версию.

MVP — это не “первая версия всего”. MVP — это минимальная версия, которая проверяет основную идею.

### Нужно определить

```text
1. Главный сценарий.
2. Минимальный набор экранов.
3. Минимальную модель данных.
4. Минимальный набор настроек.
5. Минимальный способ хранения.
6. Минимальный способ проверки результата.
```

### Формула MVP

```text
MVP = главная польза + минимальный интерфейс + минимальная надёжность
```

### Запрещено в MVP без причины

```text
1. Сложная авторизация.
2. Облачная синхронизация.
3. Несколько платформ сразу.
4. Сложная аналитика.
5. Система плагинов.
6. Красивые, но бесполезные анимации.
7. Универсальный движок на будущее.
8. Многоуровневая архитектура ради красоты.
9. Поддержка всех возможных форматов.
10. Много настроек “на всякий случай”.
```

### Результат этапа

Создать файл:

```text
docs/product/mvp-scope.md
```

Структура:

```markdown
# MVP Scope

## Главная цель MVP

## Входит в MVP

## Не входит в MVP

## Главный сценарий пользователя

## Минимальные экраны

## Минимальные данные

## Минимальная надёжность

## Критерии готовности MVP
```

### Правило выхода

Если список MVP разросся больше чем на 1–2 недели работы, его надо резать.

## 4. Этап выбора стека

### Цель

Выбрать технологии, которые решают задачу, а не выглядят модно в README.

Стек должен быть скучным, понятным и достаточным. Скучные технологии — это хорошо. Они хотя бы не требуют шаманского бубна при каждом обновлении зависимости.

### Общие правила выбора стека

```text
1. Для MVP выбирать минимум магии.
2. Не тащить тяжёлые фреймворки без причины.
3. Не выбирать технологию только потому, что она модная.
4. Не выбирать технологию, которую сложно отлаживать.
5. Не выбирать стек, который плохо работает в моей среде.
6. Не завязываться на сервисы, недоступные в России, если это критично.
7. Фиксировать версии языка, SDK и основных зависимостей.
```

### Для Android-проектов

Предпочтительный профиль:

```text
Native Android
Kotlin или Java по ситуации
Material 3
MVVM / UseCase
Room или DataStore при необходимости
WorkManager / AlarmManager по задаче
OkHttp для простого HTTP
Минимум лишних библиотек в MVP
```

Избегать в MVP без причины:

```text
Flutter
KMP
Firebase
RxJava
multi-module
сложных DI-графов
Retrofit/Ktor, если нужен простой HTTP-запрос
```

### Для Java-лаб

Стек диктуется требованиями:

```text
JDK 23
табы для отступов
Resourcer
строгая структура пакетов
минимальный public API
без изменения чужих пакетов
```

### Для web/backend-проектов

Фиксировать стек заранее:

```text
Frontend:
- React + TypeScript + Vite
- Tailwind по необходимости

Backend:
- Node.js + TypeScript
- NestJS при сложной архитектуре
- Prisma + Postgres при нормальной БД

Deploy:
- VPS
- Docker Compose
- Caddy/Nginx
- Let's Encrypt
```

### Результат этапа

Создать файл:

```text
docs/architecture/tech-stack.md
```

Структура:

```markdown
# Tech Stack

## Выбранный стек

## Почему выбран именно он

## Что сознательно не используем

## Версии языка/SDK/инструментов

## Ограничения

## Как собрать проект

## Как запустить проект

## Как протестировать проект
```

Создать структуру проекта так, чтобы её понимал не только я сегодня, но и я через месяц. Последний — особенно опасный человек, он уже ничего не помнит.

## 6. Этап архитектуры

### Цель

Разложить приложение на слои и основные компоненты до написания большого кода.

Архитектура не должна быть идеальной. Она должна быть достаточно понятной, чтобы не превратить проект в клубок проводов, который “пока не трогаем, потому что работает”.

### Базовое разделение

```text
ui/
    экраны, компоненты, отображение состояния

domain/
    бизнес-логика, use cases, правила приложения

data/
    файлы, БД, сеть, API, кэш

core/
    общие модели, ошибки, утилиты, интерфейсы

infrastructure/
    платформенные реализации, внешние сервисы
```

### Правила зависимостей

```text
ui -> domain
data -> domain/core
infrastructure -> domain/core
domain не зависит от ui
domain не зависит от конкретной платформы, если можно избежать
```

### Что нужно описать

```text
1. Основные сущности.
2. Главные сценарии.
3. Где хранить данные.
4. Как обрабатывать ошибки.
5. Где локализация/ресурсы.
6. Где внешние интеграции.
7. Где бизнес-правила.
8. Как тестировать domain-логику.
```

### Результат этапа

Создать файл:

```text
docs/architecture/architecture.md
```

Структура:

```markdown
# Architecture

## Слои

## Главные сущности

## Главные сценарии

## Поток данных

## Хранение данных

## Ошибки

## Локализация/ресурсы

## Внешние интеграции

## Тестирование

## Что запрещено
```

### Правило выхода

Если непонятно, где должна жить новая логика, архитектуру надо уточнить до кодинга.

## 7. Этап дорожной карты версий

### Цель

Разбить проект на маленькие версии.

Не “сделать приложение”, а “сделать следующую проверяемую ступень”.

### Примерная схема

```text
v0.1.0 — каркас проекта
v0.2.0 — базовая модель данных
v0.3.0 — главный сценарий
v0.4.0 — сохранение/загрузка
v0.5.0 — уведомления/интеграции
v0.6.0 — настройки
v0.7.0 — устойчивость и обработка ошибок
v0.8.0 — UI/UX полировка
v0.9.0 — релизная подготовка
v1.0.0 — первый стабильный релиз
```

### Для каждой версии описать

```text
1. Цель версии.
2. Что входит.
3. Что не входит.
4. Какие файлы/модули затрагиваются.
5. Какие проверки нужны.
6. Что тестировать вручную.
7. Критерии готовности.
```

### Файл версии

```text
docs/versions/v0.1.0.md
```

Шаблон:

```markdown
# v0.1.0 — Название версии

## Цель

## Входит в версию

## Не входит в версию

## Архитектурные ограничения

## Файлы и модули

## План реализации

## Автоматические проверки

## Ручное тестирование

## Критерии готовности

## Риски
```

### Правило выхода

Нельзя давать Cursor/Codex задачу без файла текущей версии.

## 8. Этап подготовки задачи для Cursor/Codex

### Цель

Дать AI-агенту ограниченную, проверяемую задачу.

AI без рамок — это не помощник, а стажёр с бензопилой в серверной.

### Каждый промпт должен содержать

```text
1. Контекст проекта.
2. Ссылки на документы, которые нужно прочитать.
3. Текущую версию.
4. Цель задачи.
5. Что разрешено менять.
6. Что запрещено менять.
7. Архитектурные правила.
8. Проверки после изменений.
9. Формат отчёта.
```

### Запрещено

```text
1. Просить сделать несколько версий сразу.
2. Просить “улучшить всё”.
3. Разрешать менять архитектуру без причины.
4. Разрешать переписывать проект целиком.
5. Давать огромную задачу без критериев готовности.
```

### Шаблон промпта для Cursor/Codex

```markdown
# Задача для AI-агента

## Контекст

Ты работаешь в проекте `<project-name>`.

Перед изменениями прочитай:

- `AGENTS.md`
- `docs/product/mvp-scope.md`
- `docs/architecture/tech-stack.md`
- `docs/architecture/architecture.md`
- `docs/versions/vX.Y.Z.md`

## Текущая версия

`vX.Y.Z — <название>`

## Цель

<одна конкретная цель>

## Разрешено менять

- `<path>`
- `<path>`

## Запрещено менять

- внешний/generated/vendor-код;
- архитектуру без необходимости;
- будущие версии;
- публичные API без причины;
- пользовательские строки в коде вместо ресурсов.

## Требования

1. Следуй `AGENTS.md`.
2. Работай только в рамках текущей версии.
3. Не реализуй функции будущих версий.
4. Не смешивай UI, domain и data.
5. Все пользовательские строки выноси в ресурсы.
6. После изменений запусти доступные проверки.

## Проверки

Выполни:

```bash
<commands>
```

## Отчёт

В конце напиши:

1. Что изменено.
2. Какие файлы затронуты.
3. Какие проверки выполнены.
4. Что не удалось проверить.
5. Что мне протестировать вручную.
```

### Правило выхода

Если задача не помещается в один понятный промпт, её надо разбить.

## 9. Этап реализации версии

### Цель

Сделать одну версию без расползания задачи.

### Рабочий цикл

```text
1. Создать/проверить файл версии.
2. Создать промпт для AI-агента.
3. Дать агенту только текущую задачу.
4. Проверить diff.
5. Собрать проект.
6. Запустить тесты.
7. Установить/запустить приложение.
8. Протестировать вручную.
9. Исправить найденные проблемы.
10. Закоммитить.
11. Обновить changelog.
```

### Правило против расползания

Если во время реализации появилась новая идея, она записывается в:

```text
docs/product/ideas.md
```

А не внедряется сразу.

Структура записи:

```markdown
## Идея

## Почему появилась

## Польза

## Риски

## Возможная версия
```

### Запрещено во время версии

```text
1. Добавлять функции не из текущего scope.
2. Делать большой рефакторинг “заодно”.
3. Менять стек.
4. Менять структуру проекта без причины.
5. Править старую рабочую логику без теста/проверки.
```

### Правило выхода

Версия завершена только когда:

```text
[ ] код написан;
[ ] проект собирается;
[ ] тесты проходят или честно указано, почему их нет;
[ ] ручной сценарий проверен;
[ ] changelog обновлён;
[ ] изменения закоммичены;
[ ] следующая задача не смешана с текущей.
```

## 10. Этап проверки diff

### Цель

Не принимать код от AI вслепую.

AI может быть полезным. Ещё AI может уверенно сломать проект и объяснить, что это “улучшение читаемости”. Поэтому diff проверяется всегда.

### Проверить в diff

```text
1. Нет ли случайного удаления функциональности.
2. Не изменились ли файлы вне scope.
3. Не появились ли хардкодные пользовательские строки.
4. Не появились ли странные Manager/Processor/Handler.
5. Не смешались ли UI, domain и data.
6. Не появился ли лишний public API.
7. Не появились ли зависимости без необходимости.
8. Не сломалась ли локализация.
9. Не появилась ли логика будущих версий.
10. Не изменился ли внешний/generated/vendor-код.
```

### Если diff слишком большой

```text
1. Остановиться.
2. Не принимать изменения целиком.
3. Попросить разбить на меньшие шаги.
4. При необходимости откатиться к последнему рабочему коммиту.
```

### Правило выхода

Если я не могу объяснить каждое крупное изменение в diff, его нельзя принимать.

## 11. Этап автоматических проверок

### Цель

Поймать очевидные ошибки до ручного тестирования.

### Универсальные проверки

```text
1. Сборка проекта.
2. Unit-тесты.
3. Линтер.
4. Форматтер.
5. Static analysis.
6. Проверка зависимостей.
7. Проверка отсутствия секретов.
```

### Android-проект

Примерный набор:

```powershell
.\gradlew.bat clean
.\gradlew.bat test
.\gradlew.bat lint

## 15. Этап устойчивости

### Цель

Проверить, что приложение не разваливается от обычной жизни.

Пользователь не обязан использовать приложение “правильно”. Он свернёт его, отключит сеть, удалит файл, запретит уведомления, перезагрузит телефон и потом будет удивляться. Классика жанра.

### Проверить

```text
1. Нет сети.
2. Медленная сеть.
3. Ошибка API.
4. Пустой файл.
5. Повреждённый файл.
6. Нет разрешений.
7. Нет доступа к хранилищу.
8. Перезапуск приложения.
9. Перезагрузка устройства.
10. Обновление приложения.
11. Смена времени/часового пояса.
12. Удаление/перемещение источника данных.
```

### Для фоновых задач

```text
1. Задача выполняется по расписанию.
2. Задача не дублируется.
3. Задача восстанавливается после reboot.
4. Ошибка не убивает весь цикл.
5. Пользователь получает понятное уведомление при проблеме.
```

### Результат этапа

Создать:

```text
docs/testing/reliability-checklist.md
```

## 18. Этап первого публичного релиза

### Цель

Выпустить не идеальную, а честную и проверенную версию.

Первый релиз лучше обозначать как:

```text
Beta
Pre-release
MVP

Не надо делать вид, что v1.0.0 сразу является швейцарскими часами. Это приложение, а не собор, хотя баги иногда действительно религиозного масштаба.

### Где выпускать

В зависимости от проекта:

```text
GitHub Releases
GitVerse
сайт проекта
APK-файл
закрытое тестирование
личная рассылка тестерам
```

### Что приложить

```text

3. Инструкцию установки.
4. Требования к системе.
5. Список известных проблем.
6. Как отправить feedback.
```

### Правило выхода

Релиз считается сделанным, когда другой человек может скачать, установить и понять, что тестировать.

```text

Если сработало стоп-правило:

```text

2. Зафиксировать проблему.
3. Вернуться к последнему рабочему коммиту или уменьшить scope.
4. Сделать маленький исправляющий шаг.
```

## 23. Мои правила работы с несколькими проектами

### Главный риск

Я могу начать несколько сильных проектов параллельно и распылиться.

Это выглядит продуктивно, но часто превращается в коллекцию почти готовых вещей. Почти готовое приложение приносит примерно столько же пользы, сколько почти построенный мост.

### Правило фокуса

```text
В один момент времени:
1 основной проект;
1 запасной проект;
остальные — только notes/backlog.
```

### Основной проект

```text
Проект, который я довожу до следующего релиза.
```

### Запасной проект

```text
Проект, куда можно переключиться на короткое время, если в основном блокер.
```

### Остальные идеи

```text
Только фиксировать в ideas.md.
Не начинать разработку.
```

## 29. Главное правило

Проект не считается успешным, когда “код почти написан”.

Проект считается успешным, когда:

```text
1. его можно собрать;
2. его можно запустить;
3. главный сценарий работает;
4. пользователь понимает, что делать;
5. ошибки обрабатываются нормально;
6. версия зафиксирована;
7. есть changelog;
8. есть понятный следующий шаг;
9. проект можно продолжать без переписывания с нуля.
```

Код — это не цель.
Рабочее приложение — цель.
Релиз — доказательство, что приложение действительно существует, а не просто занимает место в репозитории, как цифровой трупик с README.
