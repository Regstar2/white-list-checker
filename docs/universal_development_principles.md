# Универсальные принципы разработки приложений

## 1. Имена должны объяснять назначение

Любое имя в коде должно отвечать на вопрос: “зачем это существует?”

Это касается:
- классов;
- функций;
- методов;
- переменных;
- файлов;
- модулей;
- компонентов UI;
- таблиц базы данных;
- API endpoints;
- ресурсов;
- тестов.

Плохо:

```text
Manager
Processor
Handler
Data
Info
Helper
Utils
doWork()
process()
handle()
run()
```

Допустимо использовать такие слова только если из контекста абсолютно ясно, что именно происходит. В большинстве случаев это ленивые названия, за которыми прячется слабая архитектура.

Лучше:

```text
TaskReminderScheduler
MarkdownTaskParser
WhitelistStatusChecker
NotificationPermissionRequester
UserSettingsRepository
DownloadedTrackMatcher
```

Метод должен называться по действию:

```text
calculateOverdueTaskCount()
findSecondLargestAbsoluteValue()
loadUserSettings()
saveMarkdownTask()
sendStatusChangedNotification()
```

---

## 2. Не использовать лишние слова в названиях

Название должно быть точным, но не раздутым.

Плохо:

```text
WordSplittingProcessor
TaskProcessingManager
NotificationHandlingService
DataInformationObject
```

Лучше:

```text
WordSplitter
TaskParser
NotificationSender
TaskData
```

Правило:

```text
Если слово не добавляет смысла — удалить.
Если после удаления смысл сломался — оставить.
```

---

## 3. Один элемент — одно назначение

Каждый программный элемент должен иметь одну понятную ответственность.

Класс не должен одновременно:
- читать данные;
- парсить данные;
- хранить состояние;
- применять бизнес-правила;
- рисовать UI;
- отправлять уведомления;
- логировать аналитику;
- сохранять настройки.

Правило:

```text
Один класс — одна роль.
Один метод — одно действие.
Одна переменная — один смысл.
Один модуль — одна зона ответственности.
```

---

## 4. Одна задача должна иметь одно место реализации

Если одна и та же логика размазана по нескольким местам, это будущий баг.

Плохо:

```text
Проверка просрочки задачи есть:
- в UI;
- в ViewModel;
- в Scheduler;
- в Repository;
- в NotificationReceiver.
```

Лучше:

```text
TaskStatusCalculator отвечает за определение статуса задачи.
Все остальные классы используют его результат.
```

Правило:

```text
Если правило предметной области изменится, правка должна быть в одном месте.
```

---

## 5. Устранять дублирование не копипастой, а моделью

Дублирование бывает не только текстовое, но и смысловое.

Плохо:

```text
В трёх местах вручную проверяется:
если дата меньше текущей,
статус не completed,
задача не skipped,
значит overdue.
```

Лучше:

```text
taskStatusResolver.resolveStatus(task, currentTime)
```

Но не надо создавать абстракцию ради двух похожих строк. Абстракция нужна, когда она реально упрощает развитие проекта, а не просто делает код “умнее” на вид.

---

## 6. Делить код на уровни абстракции

В одном методе нельзя смешивать высокоуровневую бизнес-логику и низкоуровневые детали.

Плохо:

```text
completeTask():
- проверяет статус;
- меняет markdown-строку;
- открывает файл;
- пишет байты;
- отменяет alarm;
- показывает toast.
```

Лучше:

```text
completeTask():
- обновляет задачу;
- сохраняет изменение;
- отменяет напоминание.
```

А детали спрятаны ниже:

```text
TaskRepository
ReminderScheduler
TaskStatusResolver
```

Правило:

```text
Метод верхнего уровня должен читаться как сценарий.
Метод нижнего уровня должен выполнять конкретную техническую операцию.
```

---

## 7. Использовать нисходящее проектирование

Сначала проектируется общий сценарий, потом детали.

Пример:

```text
Проверить состояние белых списков:
1. загрузить источники;
2. получить текущее состояние;
3. сравнить с предыдущим состоянием;
4. сохранить результат;
5. уведомить пользователя при изменении.
```

Потом каждый шаг раскрывается отдельными классами/методами:

```text
WhitelistSourceLoader
WhitelistStatusChecker
WhitelistStatusComparator
WhitelistStateRepository
StatusChangeNotifier
```

Так код получается читаемым, а не превращается в кашу, которую потом героически называют “итеративной разработкой”.

---

## 8. Пользовательские строки всегда выносить в ресурсы

Все строки, которые видит пользователь, должны лежать в ресурсах, а не в коде.

К пользовательским строкам относятся:
- заголовки экранов;
- тексты кнопок;
- сообщения ошибок;
- подсказки;
- статусы;
- уведомления;
- описания настроек;
- тексты пустых состояний;
- тексты подтверждений;
- тексты в логах, если они предназначены пользователю или поддержке.

Плохо:

```text
showMessage("Файл не найден")
```

Лучше:

```text
showMessage(resourceProvider.getFileNotFoundMessage())
```

В зависимости от языка и платформы это могут быть:

```text
strings.xml
.json localization files
.arb files
.resx files
.properties files
i18n dictionaries
```

Универсальное правило:

```text
Код не должен быть хранилищем пользовательского текста.
Код должен ссылаться на ресурс.
```

Исключения:
- внутренние технические сообщения для разработчика;
- временные debug-логи;
- тестовые фикстуры;
- сообщения, которые никогда не попадут пользователю.

---

## 9. Ресурсы должны быть централизованы

Нельзя раскидывать пользовательские строки по проекту.

Нужен единый слой доступа:

```text
ResourceProvider
TextResources
StringResolver
LocalizationService
Resourcer
```

Название зависит от языка и платформы, но идея одна:

```text
UI и бизнес-логика не должны напрямую знать, где именно лежит текст.
```

---

## 10. Не смешивать бизнес-логику и локализацию

Бизнес-логика должна возвращать не готовую фразу, а результат, код ошибки или статус.

Плохо:

```text
return "Задача просрочена";
```

Лучше:

```text
return TaskStatus.OVERDUE;
```

А UI уже превращает это в текст:

```text
resourceProvider.getTaskStatusText(TaskStatus.OVERDUE)
```

Правило:

```text
Внутри программы должен быть статус, код или тип.
Для пользователя должен быть локализованный текст.
```

---

## 11. Явно указывать область видимости

У каждого класса, метода, свойства и функции должна быть минимально необходимая область доступа.

Правило:

```text
По умолчанию всё private/internal.
Public только то, что реально является внешним API модуля.
```

Плохо:

```text
public всё подряд, потому что так быстрее.
```

Лучше:

```text
public — только входные методы;
private — детали реализации;
protected — только если наследование действительно нужно;
internal/package-private — для границ модуля.
```

Если всё public, то у проекта не архитектура, а проходной двор.

---

## 12. Public API должен быть маленьким

Чем больше публичных методов у класса, тем сложнее его безопасно менять.

Правило:

```text
Публичные методы — это контракт.
Приватные методы — это реализация.
```

Перед тем как сделать метод public, нужно ответить:

```text
Кто будет его вызывать?
Почему нельзя оставить private?
Это часть сценария использования или техническая деталь?
```

---

## 13. Сначала публичный интерфейс, потом детали

Внутри класса удобнее располагать код так:

```text
1. Константы
2. Поля
3. Конструктор
4. Public методы
5. Internal/protected методы
6. Private методы
```

Смысл:

```text
Сначала читатель видит, как класс используется.
Потом — как он устроен внутри.
```

Это не всегда строго обязательно, но как общее правило работает хорошо.

---

## 14. Конструктор должен создавать валидный объект

Объект после создания должен быть готов к работе.

Плохо:

```text
user = new User()
user.setName(...)
user.setAge(...)
user.setEmail(...)
```

Лучше:

```text
user = new User(name, age, email)
```

Или:

```text
user = User.create(name, age, email)
```

Правило:

```text
Не создавать объект в полурабочем состоянии.
```

---

## 15. Избегать setter-ов без необходимости

Сеттеры часто превращают объект в мешок состояния.

Плохо:

```text
task.setTitle(...)
task.setDueDate(...)
task.setRepeatRule(...)
task.setPriority(...)
```

Лучше:

```text
task = task.withUpdatedDueDate(newDueDate)
```

Или:

```text
taskEditor.changeDueDate(taskId, newDueDate)
```

Универсальное правило:

```text
Изменение состояния должно быть осмысленным действием, а не произвольной записью в поле.
```

Исключения:
- DTO;
- UI form state;
- ORM-модели;
- сериализация;
- простые структуры конфигурации.

---

## 16. Не отдавать наружу изменяемые внутренности объекта

Если объект хранит массив, список, словарь, map, mutable collection или файл, нельзя просто отдавать внутреннюю ссылку наружу.

Плохо:

```text
return internalTasks;
```

Лучше:

```text
return immutableCopy;
```

Или:

```text
getTaskAt(index)
getTaskCount()
replaceTaskAt(index, task)
```

Правило:

```text
Объект сам контролирует своё состояние.
Внешний код не должен ломать его изнутри.
```

---

## 17. Сокращать длинные списки параметров

Если у функции или конструктора слишком много параметров, часть из них нужно объединить в объект-данные.

Плохо:

```text
createNotification(title, text, channelId, priority, icon, actionText, actionId, vibration, sound)
```

Лучше:

```text
createNotification(notificationRequest)
```

Где:

```text
NotificationRequest
- title
- text
- channelId
- priority
- actions
- soundSettings
```

Правило:

```text
Если параметры логически связаны — они заслуживают отдельную модель.
```

---

## 18. Использовать параметры вместо скрытого состояния

Функция должна по возможности получать нужные данные явно, а не вытаскивать их из глобальных переменных, полей, singleton-ов и магических констант.

Плохо:

```text
calculateStatus() использует currentTime из глобального объекта.
```

Лучше:

```text
calculateStatus(task, currentTime)
```

Плюсы:
- проще тестировать;
- меньше скрытых зависимостей;
- легче понять код;
- меньше магии.

---

## 19. Глобальные зависимости внедрять, а не создавать внутри

Класс не должен сам создавать сложные зависимости, если они являются частью инфраструктуры.

Плохо:

```text
class TaskService {
    repository = new FileTaskRepository()
    scheduler = new AndroidReminderScheduler()
}
```

Лучше:

```text
class TaskService {
    constructor(repository, scheduler)
}
```

Правило:

```text
Бизнес-класс не должен сам решать, какую базу данных, файловую систему, API-клиент или планировщик использовать.
```

---

## 20. Зависеть от абстракций, а не от конкретных реализаций

Плохо:

```text
TaskService зависит от SQLiteTaskRepository.
```

Лучше:

```text
TaskService зависит от TaskRepository.
SQLiteTaskRepository реализует TaskRepository.
```

Так можно заменить:
- файл на БД;
- локальный источник на сетевой;
- реальный API на fake-объект в тестах;
- Android-планировщик на desktop-планировщик.

Правило:

```text
Стабильная логика зависит от интерфейсов.
Конкретные детали подключаются снаружи.
```

---

## 21. Соблюдать правило Деметры

Объект не должен лазить по длинным цепочкам чужих внутренностей.

Плохо:

```text
user.getProfile().getSettings().getNotificationConfig().getChannelId()
```

Лучше:

```text
user.getNotificationChannelId()
```

Или:

```text
notificationSettings.getChannelId()
```

Правило:

```text
Не разговаривай с внутренностями чужих внутренностей.
```

Если в коде много цепочек через точки, скорее всего структура данных протекла наружу.

---

## 22. Не менять внешний, сгенерированный или чужой код напрямую

Если есть сторонний пакет, библиотека, generated-файлы, SDK-код или код преподавателя/платформы, его нельзя править без крайней необходимости.

Вместо этого использовать:
- адаптер;
- wrapper;
- facade;
- mapper;
- extension-слой;
- отдельную реализацию интерфейса.

Плохо:

```text
Править vendor-код, потому что так быстрее.
```

Лучше:

```text
Создать адаптер вокруг vendor-кода.
```

Правило:

```text
Чужой код — это граница системы.
Свои изменения должны жить в своём слое.
```

---

## 23. Избегать длинных методов

Длинный метод почти всегда означает, что в нём несколько действий.

Признаки плохого метода:
- много условий;
- несколько циклов подряд;
- вложенные циклы;
- разные уровни абстракции;
- много временных переменных;
- комментарии вида “теперь делаем X”;
- метод трудно назвать одним глаголом.

Правило:

```text
Если метод нельзя кратко описать одной фразой, его нужно разделить.
```

---

## 24. Не складывать несколько независимых циклов в один метод

Если метод содержит несколько циклов подряд, часто это значит, что он делает несколько разных действий.

Плохо:

```text
buildReport():
- цикл собирает ошибки;
- цикл собирает предупреждения;
- цикл собирает успешные элементы.
```

Лучше:

```text
buildReport():
- collectErrors()
- collectWarnings()
- collectSuccessfulItems()
```

Важно: это не абсолютный запрет. В нормальной разработке иногда несколько циклов в одном методе оправданы. Но если они решают разные задачи — лучше разнести.

---

## 25. Осторожно использовать вложенные циклы

Вложенные циклы допустимы, если задача реально требует сравнения “каждый с каждым” или обхода двумерной структуры.

Но если вложенность растёт, надо подумать:
- можно ли вынести внутреннюю логику в метод;
- можно ли использовать индекс/словарь/map;
- можно ли изменить структуру данных;
- не стал ли алгоритм слишком дорогим.

Правило:

```text
Вложенный цикл должен быть очевидно оправдан.
```

---

## 26. Не использовать бесконечные циклы без явного условия выхода

Плохо:

```text
while true
```

Лучше:

```text
while applicationIsRunning
while hasNextPage
while retryCount < maxRetryCount
```

Если бесконечный цикл действительно нужен, условие выхода должно быть явно описано внутри и хорошо протестировано.

---

## 27. Не прятать сложную логику в тернарные выражения

Тернарный оператор допустим для простых выражений.

Нормально:

```text
label = isCompleted ? completedText : activeText
```

Плохо:

```text
status = a ? b : c ? d : e ? f : g
```

Универсальное правило:

```text
Если условие нужно читать два раза — пиши обычный if.
```

Для учебных Java-лаб можно полностью запрещать тернарный оператор. Для реальных проектов полный запрет не нужен.

---

## 28. Не использовать “умные” решения без практической пользы

Код должен быть не интересным, а полезным.

Плохо:
- сложная иерархия ради одной операции;
- паттерн ради паттерна;
- универсальный движок там, где нужна одна функция;
- метапрограммирование без причины;
- магия, которую нельзя нормально отладить.

Правило:

```text
Сначала практичность.
Потом красота.
Потом универсальность.
```

---

## 29. Константы должны иметь смысловое имя

Магические числа и строки нельзя оставлять в коде.

Плохо:

```text
if retryCount > 3
if status == "done"
delay = 5000
```

Лучше:

```text
MAX_RETRY_COUNT
COMPLETED_STATUS_CODE
DEFAULT_RETRY_DELAY_MS
```

Но не надо выносить очевидные локальные значения без смысла. Константа нужна там, где значение имеет предметный смысл.

---

## 30. Не держать предметные константы внутри случайных методов

Если значение относится к бизнес-правилу, оно должно лежать рядом с этим правилом.

Плохо:

```text
method calculateDiscount():
    maxDiscount = 30
```

Лучше:

```text
DiscountPolicy.MAX_DISCOUNT_PERCENT
```

Или:

```text
discountPolicy.getMaxDiscountPercent()
```

Правило:

```text
Константа должна жить там, где живёт смысл этой константы.
```

---

## 31. Код должен быть форматирован единообразно

В проекте должен быть один стиль:
- отступы;
- пробелы;
- порядок импортов;
- длина строки;
- правила переноса;
- расположение скобок;
- порядок методов;
- стиль именования.

Это должно проверяться автоматически:
- formatter;
- linter;
- static analyzer;
- checkstyle;
- detekt;
- eslint;
- prettier;
- ruff;
- ktlint;
- dart analyze.

Правило:

```text
Форматирование не должно быть предметом спора людей.
Пусть этим занимается инструмент.
```

---

## 32. Версии языка, SDK и зависимостей фиксировать

Проект должен явно указывать:
- версию языка;
- версию SDK;
- версию runtime;
- версию сборщика;
- ключевые зависимости;
- минимальную поддерживаемую платформу.

Плохо:

```text
“У меня работает”
```

Лучше:

```text
Java 23
Android minSdk 26 / targetSdk 35
Flutter 3.x
Python 3.12
Node 22
```

Правило:

```text
Среда разработки — часть проекта.
```

---

## 33. Структура проекта должна отражать архитектуру

Папки не должны быть случайными.

Плохо:

```text
utils/
managers/
misc/
new/
old/
test2/
```

Лучше:

```text
domain/
data/
ui/
core/
infrastructure/
features/
tests/
resources/
```

Для feature-based архитектуры:

```text
features/tasks/
features/calendar/
features/settings/
shared/domain/
shared/ui/
shared/data/
```

Правило:

```text
По структуре проекта должно быть понятно, где искать нужный код.
```

---

## 34. Ввод, вывод и бизнес-логику разделять

Код, который получает данные, не должен одновременно решать предметную задачу и показывать результат.

Плохо:

```text
readInputAndCalculateAndPrintResult()
```

Лучше:

```text
inputReader.read()
calculator.calculate(input)
outputPrinter.print(result)
```

Правило:

```text
Ввод — отдельно.
Обработка — отдельно.
Вывод — отдельно.
```

---

## 35. Ошибки должны быть частью модели, а не случайной строкой

Плохо:

```text
return "Ошибка"
```

Лучше:

```text
Result.failure(ErrorCode.FILE_NOT_FOUND)
```

Или:

```text
Either<DomainError, Result>
```

Потом UI превращает ошибку в текст через ресурсы.

Правило:

```text
Внутри программы ошибка — это тип/код/объект.
Для пользователя ошибка — это локализованный текст.
```

---

## 36. Не проглатывать ошибки молча

Плохо:

```text
catch error:
    pass
```

Лучше:

```text
log error
return failure
show meaningful message
```

Исключение может быть только если ошибка ожидаемая и безопасная, но даже тогда это должно быть понятно из кода.

---

## 37. Данные должны быть валидны на границах системы

Проверять данные нужно там, где они входят в систему:
- пользовательский ввод;
- файл;
- API;
- база данных;
- intent;
- deep link;
- настройки;
- аргументы командной строки.

Правило:

```text
Внутри domain-слоя лучше работать уже с валидными моделями.
```

---

## 38. DTO, domain model и UI model не должны смешиваться

Внешние модели нельзя тащить через всё приложение.

Плохо:

```text
APITrack используется в UI, domain и data.
```

Лучше:

```text
APITrack -> TrackEntity -> Track -> TrackUiModel
```

Правило:

```text
Каждый слой имеет свои модели, если внешняя модель нестабильна или неудобна.
```

---

## 39. Не делать зависимости неочевидными

Если класс зависит от времени, файловой системы, сети, настроек, локали или платформы, это должно быть видно.

Плохо:

```text
TaskStatusCalculator внутри сам берёт текущее время.
```

Лучше:

```text
TaskStatusCalculator(clock)
```

Или:

```text
calculateStatus(task, currentTime)
```

Правило:

```text
Скрытая зависимость — будущий тестовый кошмар.
```

---

## 40. Для неочевидного создания объектов использовать фабрики

Если объект сложно создать, не надо размазывать его создание по проекту.

Плохо:

```text
В десяти местах создаётся один и тот же набор зависимостей.
```

Лучше:

```text
TaskFeatureFactory
NotificationModule
AppContainer
CompositionRoot
```

Правило:

```text
Сложная сборка зависимостей должна быть централизована.
```

---

## 41. Не писать универсальный код раньше времени

Абстракция нужна, когда:
- есть минимум две реальные реализации;
- есть понятная точка расширения;
- есть тестовая польза;
- есть риск смены внешнего источника.

Абстракция не нужна, если:
- она создана “на всякий случай”;
- она усложняет чтение;
- она скрывает простую операцию;
- её нельзя объяснить без диаграммы.

---

## 42. Правила можно нарушать, но нарушение должно быть осознанным

Некоторые правила иногда конфликтуют.

Например:
- один ранний return может сделать код проще;
- два маленьких цикла могут быть понятнее одной хитрой абстракции;
- тернарный оператор может быть читаемым;
- прямой вызов зависимости может быть нормален в маленьком скрипте.

Правило:

```text
Если нарушение улучшает читаемость и снижает сложность — оно допустимо.
Если нарушение просто экономит 30 секунд — это технический долг.
```

---

## 43. AI-агент должен соблюдать эти правила

При работе через Cursor/Codex/ChatGPT агент обязан:

```text
1. Сначала читать правила проекта.
2. Не менять архитектуру без явной причины.
3. Не добавлять public API без необходимости.
4. Не смешивать UI, domain и data.
5. Не хардкодить пользовательские строки.
6. Не создавать классы Manager/Processor/Handler без точного смысла.
7. Не плодить абстракции без реальной пользы.
8. Не менять внешний/generated/vendor-код.
9. После изменений сообщать:
   - что изменено;
   - какие файлы затронуты;
   - какие проверки выполнены;
   - что нужно протестировать вручную.
```

---

## 44. Что не стоит делать универсальным правилом

Некоторые требования полезны только для конкретной учебной среды.

Не стоит универсально запрещать:

```text
foreach
коллекции
тернарный оператор
несколько циклов в одном методе
все setter-ы
все вложенные циклы
```

В реальных проектах это нормальные инструменты. Запрещать их полностью — всё равно что запретить молоток, потому что кто-то однажды ударил себя по пальцу.

Правильный универсальный вариант:

```text
Использовать foreach, коллекции, setter-ы, тернарные выражения и циклы только там, где они улучшают читаемость, безопасность и простоту.
```

---

## 45. Главный итоговый принцип

Код должен быть:

```text
понятным;
локализуемым;
тестируемым;
разделённым по ответственности;
с явными зависимостями;
с минимальным public API;
без случайного дублирования;
без скрытого состояния;
без пользовательских строк внутри логики;
с архитектурой, которую можно развивать.
```

Хороший код — это не тот код, где использованы все паттерны.
Хороший код — это тот код, который через месяц можно открыть и понять без желания вызвать экзорциста.
